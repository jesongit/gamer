# 通知助手

安装并启用通知助手后，在工作台添加企微连通道，填入调用密钥，点「测试」。通道是全局配置，不绑定配置包；新增通道可以填写稳定 ID，供任务和脚本引用。调用密钥不会从接口读回。

任务编辑页的「运行结果通知」可按成功、失败、取消、跳过分别选择多个通道，并设置标题、正文。默认关闭。未安装通知插件时也能编辑和保存这些配置，实际执行跳过通知并记录原因，任务继续按自身结果完成。重新安装不会补发历史通知。

自动化使用 `notify` 普通函数，语法见 [YAML 参考](../reference/YAML.md)。缺少通知插件时，该步骤仍可加入、编辑和保存；执行返回 skipped，后续步骤继续。自动化通知和任务结果通知是两条独立消息。

留空的任务标题和正文使用默认摘要，可使用以下变量：`{{task.name}}`、`{{task.id}}`、`{{device.name}}`、`{{device.id}}`、`{{result}}`、`{{time}}`、`{{elapsed}}`、`{{error}}`、`{{entrypoint}}`、`{{run.id}}`。

「发送记录」区分已提交、发送中、接口已接受、部分成功、处理中、失败、未知和未发送。「接口已接受」不代表手机已收到；结果未知不会自动重发，获得远端记录 ID 时可以查询结果。

消息目前仅为文本，标题、换行和正文合计最多 2048 个 UTF-8 字节。通道删除或停用后，任务和脚本引用保留；恢复通道或修改引用后供未来运行使用。

通知助手 0.1.0 和支持 `notify` 的自动化插件 0.1.3 需要 Gamer 宿主 0.2.7 或更新版本。通知助手是 builtin 插件，执行代码随宿主发布；旧宿主可能因缺少实现（`host_feature_unavailable`）或不认识 `notify.send` 权限而拒绝归档，应先升级宿主再安装插件。市场目录与归档的 `execution.host_version` 是展示用兼容声明，不代替实际能力检查。

## 已有用户升级

此次宿主启动会将数据库从 schema v6 迁移到 v7，为任务增加通用的 `extensions_json` 字段，默认值为 `{}`。原有任务的调度、执行目标和参数保留，通知默认关闭；无需重新创建任务或手动执行 SQL。迁移与版本号更新在同一事务中，失败时回滚该次迁移并拒绝启动。

触发数据库迁移的是宿主升级启动，安装或卸载通知插件不会触发迁移。全局通道、调用密钥和发送记录保存在 `data/extension-data/gamer-notify/`，不在主数据库中，也不随配置包导入导出。以后添加发送渠道无需再次修改任务表。

通过内置更新流程升级时，更新器先停止旧服务，备份并校验完整数据目录和配置，再切换候选版本；候选启动或激活失败时尝试恢复升级前快照和旧版本。快照或恢复失败会明确报错，不应通过删除数据库处理。流程见 [便携安装与更新契约](UPDATE_CONTRACT.md)。

手动替换程序时，先停止服务并备份完整 `data/` 和配置文件，再替换宿主与配套前端并启动。直接启动服务端不会自动创建完整备份。开发目录通常对应 `server/data/` 和 `server/config.toml`；使用自定义路径时以实际生效配置为准。

旧宿主不支持 schema v7，回退必须恢复升级前的数据快照，再运行匹配的旧版本。卸载通知插件只停用通知能力，保留通道配置和任务引用，不降低数据库版本；重新安装也不补发历史通知。

## 发行顺序

正式发行先让包含通知能力的宿主基线提交可供 CI 检出，并将插件 `sdk/lock.json` 固定到该基线；插件 SDK 文件哈希和集成测试都要通过。随后发布包含通知助手 0.1.0 和自动化 0.1.3 的完整插件快照，再将主仓 `release/plugins.lock.json` 更新为该公开发行的提交、地址、大小和 SHA256，最后发布 Gamer 0.2.7。宿主发行只消费已发布并固定哈希的插件，不以本地构建文件或尚未发布的地址代替发布锁；插件源码提交和发布锁不一致时，打包门禁会拒绝发行。
