请对当前 gamer 项目执行一次独立的浏览器功能与交互体验验收。

本次是验收任务，不是开发任务：
- 使用你已有的浏览器工具实际操作应用。
- 默认只检查、复现、记录问题，不修改业务代码、现有测试或产品设计。
- 不要求新建自动化测试框架，也不要求把本次操作全部写成测试脚本。
- 不因单测和构建通过，就判定浏览器验收通过。

【验收范围】

检查当前公共界面及所有实际可用插件的核心用户流程。

以当前仓库和运行环境为准，先列出准备检查的功能范围，再开始操作。
不要只检查最近修改的文件，也不要只检查页面能否打开。
无法覆盖的模块或场景必须在最终报告中明确列出。

【环境与安全】

1. 阅读项目现有启动说明，优先复用已有启动命令和测试资源。
2. 使用隔离的测试实例、数据目录、配置包及测试素材。
3. 创建、保存、更新、卸载、删除等操作只能针对测试数据和测试实例，
   不得影响用户正在使用的插件、配置、设备任务或其他真实数据。
4. 不得为了运行验收而擅自升级依赖、修改业务代码或调整产品行为。
5. 环境无法启动、缺少设备或素材时，记录具体阻塞原因。
   可以继续检查不受影响的部分，但不得把未执行的部分写成通过。

【验收方式】

第一轮：从用户视角完成任务。

先通过 README、用户说明和页面了解功能目标，不要先深入实现代码，
再照着内部实现验证自己已经知道的点击路径。

围绕“用户要完成什么”组织验收，例如：
- 管理插件并进入对应功能区；
- 创建或选择配置包，编辑、保存并重新打开内容；
- 使用可视化编辑器创建一个有实际参数和资源引用的步骤；
- 从视频素材制作可供其他功能使用的资源；
- 创建、保存并应用映射配置。

实际任务应根据当前具备的功能调整。

每条任务同时检查：
- 功能：能否完全通过界面完成，必要入口和参数是否齐全。
- 结果：数据、当前上下文和最终状态是否正确。
- 体验：入口是否易找、提示是否明确、是否要求不必要的绕路操作。
- 恢复：取消、输入错误、保存失败或切换上下文后，能否继续操作。

每个模块至少完成一条核心操作闭环，并补充与该模块相关的关键异常场景。
不要只逐个点击按钮，也不要只验证成功路径。

第二轮：对发现的问题复现和定位。

遇到问题后，再结合控制台、网络请求、接口约定和代码定位原因。
没有直接证据时，只写“疑似原因”，不要猜测后当成结论。

【重点检查】

- 后端提供给用户使用的能力，前端是否有完整且可发现的操作入口。
- 可视化编辑支持的参数是否可以填写，必填项是否有明确校验。
- 保存后重新打开，内容和资源引用是否保持正确。
- 当前 Package、设备、插件和编辑对象是否一致。
- 操作过程中是否有反馈，重复点击是否造成重复执行。
- 操作失败后，输入内容是否保留，是否存在明确的重试或恢复方式。
- 切换页面或上下文时，未保存内容是否得到合理保护。
- 系统能代办的必要步骤，是否被不合理地推给用户手工完成。
- 窗口较窄、内容较多或名称较长时，是否出现遮挡、截断或无法操作。

必须查看实际截图，不得只依赖页面结构判断布局体验。

API 或脚本可以用于准备测试数据和核验结果，
但不得代替本应通过页面完成的用户操作。
不能通过修改内部状态、直接调用业务 API 等方式绕过缺失的前端入口，
然后宣称任务通过。

【输出要求】

输出一份验收报告，包含：

1. 验收环境与范围。
2. 已执行的用户任务，以及通过、失败、阻塞的结果。
3. 未检查的模块或场景。
4. 按影响程度排序的问题清单。

每个问题包含：
- 所属模块和问题类型：功能错误 / 体验问题 / 优化建议。
- 前置条件。
- 最小复现步骤。
- 预期行为与实际行为。
- 用户影响。
- 截图；必要时附控制台或网络证据。
- 已定位的相关代码位置；未定位则明确说明。

预期行为应优先依据明确需求、用户说明和数据安全要求。
仅属于主观偏好的改进，要标为“优化建议”，不要直接判为缺陷。

报告只记录真实执行结果，不编造截图、日志或测试结论。
完成报告后停止，不自动开始修复。
