# Gamer 视频工作台插件开发计划

> 状态：设计决策已确认，待实施  
> 日期：2026-09-07  
> 适用项目：`jesongit/gamer`，当前 V3 插件化架构  
> 建议实施位置：`docs/plans/gamer_video_workbench_development_plan.md`

## 1. 目标与已确认决策

本计划解决一个核心问题：游戏中的某些操作只能执行一次，或者重复准备成本很高。用户应能够把操作过程录制下来，之后脱离真实设备反复查看、逐帧分析、制作模板，并借助录制的操作事件编写自动化脚本；同时允许导入其他人录制的视频作为素材。

已确认以下决策，不再作为开发阻塞项：

| 决策 | 最终方案 |
| --- | --- |
| 画面架构 | Core 提供通用画面来源，支持实时设备与离线视频；视频不是伪装设备 |
| 操作录制 | 第一版同步录制视频与操作事件，支持辅助生成脚本草稿 |
| 分辨率 | 推荐 1920×1080 制作环境，不强制 1080p+；其他分辨率允许导入并进行校准 |
| 素材存储 | 原视频放全局媒体库，Package 保存项目数据和素材引用；导出时可显式包含素材 |
| V1 范围 | 完成录制、导入、播放、逐帧、标记、操作事件、创建和测试模板、生成操作草稿；不做 AI 自动识别及复杂剪辑 |

最终职责：**Core 管理媒体与画面，`gamer.video` 管理录像制作工作流，`gamer.yaml` 负责模板与脚本语义。**

### 1.1 预期用户流程

```text
连接设备 → 选择 Package → 开始录制会话
       → 执行一次性操作 → 停止并保存
       → 切换视频来源 → 逐帧查看 / 时间轴标记
       → 从画面创建模板 → 在录像中测试模板
       → 选择操作事件 → 生成 YAML 草稿 → 人工完善
       → 切回实时设备 → 显式运行和验证
```

外部素材的流程为：导入视频 → 探测与画面校准 → 播放、标记 → 创建模板 → 手动编写脚本。没有操作事件时不承诺自动还原真实输入。

### 1.2 不在 V1 范围

- AI 自动识别游戏操作、自动生成完整可靠脚本。
- 视频剪辑软件式的多轨编辑、转场、字幕、特效或云端素材同步。
- 自动把录像操作发送到真实设备进行机械回放。
- 通过视频模拟 Android 设备，或让现有 Runner 在假设备上执行。
- 要求所有外部视频必须达到 1080p，或承诺一套模板在任意 UI 比例下通用。
- 为本功能恢复旧 Package Workspace、旧 YAML DSL、内置业务页签等已移除架构。

## 2. 当前仓库基线与改造落点

本计划基于 2026-09-07 可访问的 `main` 源码、README、`AGENTS.md` 和 V3 架构计划编制。实施前应以工作树最新代码为准核对接口，不将下文提出的新文件、新 API 当作已存在的实现。

当前已经具备：Rust + axum + webrtc-rs 服务端、Vue3/Vite 前端、scrcpy H.264 帧及 PTS、WebRTC 推流、GOP 缓存与 FFmpeg 按需解码、NCC 视觉引擎、`FrameHandle` / `FrameService` / `VisionService`、扩展权限与 Host API、PackageStore、官方 `gamer.yaml` 和 `gamer.keymap` 扩展。

需要重点检查和修改的现有位置：

## 3. 总体架构

```text
                       ┌──────────────────────────────┐
                       │       Core 前端壳             │
                       │ StageSource / 画面舞台        │
                       │ 实时投屏 | 离线媒体           │
                       │ 坐标 / 框选 / 叠加层 / 安全门禁│
                       └──────────────┬───────────────┘
                                      │ 通用 UI Bridge
                 ┌────────────────────┴────────────────────┐
                 │                                         │
       ┌─────────▼──────────┐                    ┌─────────▼──────────┐
       │ gamer.video 插件    │                    │ gamer.yaml 插件     │
       │ 素材 / 时间轴 / 标记│──类型化贡献调用──▶│ 模板 / 匹配 / YAML   │
       │ 会话 / 操作草稿选择 │                    │ 编辑器 / Runner     │
       └─────────┬──────────┘                    └─────────┬──────────┘
                 │ Media Host API                           │ Vision / Resource
       ┌─────────▼──────────────────────────────────────────▼─────────┐
       │                         Core                                │
       │ MediaService / MediaStore / RecordingService / FrameService │
       │ InputObserver / VisionService / PackageStore / 权限与资源租约 │
       └─────────┬────────────────────────────────────────────────────┘
                 │
       ┌─────────▼──────────────────────┐
       │ scrcpy 编码帧 + 输入分发       │
       │   ├─ WebRTC 实时播放           │
       │   ├─ GOP 缓存 / 实时视觉       │
       │   └─ 按需录制 / 事件记录       │
       └────────────────────────────────┘
```

### 3.1 Core 应该新增的能力

1. **MediaService**：导入、探测、读取媒体、提取指定帧、管理媒体句柄、生成工作副本。
2. **RecordingService**：管理设备录制会话、原始编码流封装、状态、停止与恢复。
3. **MediaStore**：全局素材元数据、文件生命周期、引用、完整性、配额与垃圾回收。
4. **InputObserver**：统一观察已经接受的输入操作，为录制器提供结构化事件，不负责解释 YAML。
5. **StageSource / StageController**：前端统一画面来源、坐标系、框选及只读门禁。
6. **离线 Frame Provider**：把媒体中的确定帧转换为现有视觉引擎可消费的帧句柄。
7. **扩展调用与 UI Bridge 能力**：安全地把当前帧、素材引用和选中事件交给其他插件。

Core 不应出现 `create_yaml_script`、`save_game_template`、`video_project` 等业务语义，也不应把视频工作台作为永久内置主页签。

### 3.2 插件划分

`gamer.video` 是独立可安装、可卸载的官方插件。建议采用现有 `.gplugin` 扩展机制，Native/WASM 运行时由真实能力需求决定，不为了“插件化”强制把 FFmpeg、文件操作、视频封装放进 WASM guest。媒体处理由 Core 的受控 Host 能力执行，插件只持有逻辑句柄。

`gamer.yaml` 继续拥有 YAML v3 语法、模板数据格式、模板引用、脚本编辑及执行能力。视频插件不得复制 YAML parser、模板存储器或脚本 Runner。跨插件通信必须经过受控的贡献/命令注册接口，不直接 import 对方前端私有模块，也不直接写对方资源目录。

## 4. 画面来源与前端设计

### 4.1 左侧统一舞台

左侧保持现有投屏布局，在投屏顶部附近提供“实时 / 视频”来源切换和轻量媒体控制。实时模式沿用设备连接、启动应用、输入控制和 WebRTC 状态。视频模式展示名称、时间、播放/暂停、逐帧、倍速、返回实时等功能，允许框选和视觉叠加，但不允许向设备发送输入。

右侧仍保持现有主导航（任务、日志、设置、市场、插件）和插件二级页签。安装 `gamer.video` 后，才在插件菜单中出现视频工作台；其内部提供素材库、时间轴/会话等页面。插件可以贡献舞台工具和右侧面板，但不能拥有整个 Core 投屏区域，也不能替换现有设备连接机制。

### 4.2 StageSource 契约（拟新增）

建议统一暴露只读的来源描述与画面操作。下列为设计契约，不是现有代码：

```ts
interface StageSource {
  kind: 'live' | 'media'
  sourceId: string
  generation: number
  displaySize: { width: number; height: number }
  referenceSize: { width: number; height: number }
  transform: FrameTransform
  canDeviceInput: boolean
  frameAt?: { mediaId: string; ptsUs: number; frameIndex?: number }
}
```

`generation` 在来源切换或校准改变时递增。任何异步截图、裁切或匹配结果必须携带来源 ID 与 generation；结果过期时不得偷偷应用到新的画面。`canDeviceInput` 只是 UI 提示，真正的输入授权仍在服务端，不能依赖浏览器布尔值保证安全。

来源切换不改变真实设备连接，也不停止已经显式启动的自动化任务。视频模式下的物理键盘、按键映射、鼠标触控、滚轮和插件输入请求均不得因为舞台焦点而误发到真机；舞台当前处于媒体模式时，所有“由舞台产生”的设备输入要在统一输入路由处拒绝。其他独立运行中的任务仍遵循原有设备/Runner 权限与生命周期，不因打开录像被假定暂停。

切回实时模式时不自动执行录制事件，也不自动恢复按键按下状态；必须清理指针、键盘焦点和旧来源叠加层。多个浏览器观看同一设备时，画面来源切换属于各自的 viewer 状态，不应全局改变其他人的投屏。

### 4.3 当前组件改造

将现有 `ConsoleVideoStage.vue` 中的媒体元素、连接状态、输入处理、坐标换算、裁切和叠加层逐步拆分为通用舞台容器、实时源 adapter、媒体源 adapter 及可复用的画面选择/叠加能力。具体文件名按当前前端组织确定，不为了拆分而制造过多小组件。

模板裁切必须变成“对指定 `FrameHandle` 或不可变图片进行裁切”，不能在用户点击保存时重新抓取最新设备画面。媒体播放器的定位与精确帧提取应分离：浏览器 `<video>` 用于流畅预览，制作模板时调用服务端确定帧接口，避免 seek 后拿到尚未更新的旧画面。

## 5. 录制与操作事件

### 5.1 视频录制路径

录制器接在 scrcpy 原始编码帧分发之后、WebRTC 播放节流和重放处理之前。保留现有实时 GOP 缓存职责；录制器自行维护必要的起始参数集和关键帧状态，不依赖 GOP 缓存上限保存完整视频。

```text
scrcpy H.264 + PTS
    ├─ 现有 WebRTC
    ├─ 现有 FrameCache / Vision
    └─ RecordingService（按需订阅）
           → 有界队列 → 封装器 → 临时文件 → finalize → 媒体库
```

默认 H.264 MP4，尽量直接 remux，不重新编码。是否增加 MKV 或分段容错由封装器实现确定；音频可作为后续可选能力，V1 不以音频为完成条件。不得录制浏览器窗口，也不得因为浏览器不在前台导致录制中断。

录制启动应等待可解码的 IDR 和有效参数集，必要时请求新关键帧。时间戳使用原始媒体 PTS 映射至录制时间基准，不使用“假设 30fps 后逐帧累加”的方式。处理 PTS 异常、重复/非单调时间戳、编码参数变化、设备断连和异常退出。分辨率或编码配置变化时，不允许默默把不兼容帧写进同一固定参数的视频轨；可选择分段并建立会话时间轴，或者安全停止并给出明确错误，V1 优先采用分段方式保留已录素材。

录制器必须有有界队列、磁盘空间检查、大小/时长配额、任务取消、状态上报和后台回收。磁盘慢或写入失败时不能阻塞 scrcpy 采集与 WebRTC；应标记录制失败/不完整，尝试安全收尾，并将缺失区间写入会话元数据。不能静默丢帧后仍宣称录像完整。

### 5.2 录制状态

建议状态：`preparing → recording → finalizing → completed`，异常进入 `interrupted / failed`，用户可取消进入 `cancelled`。服务端记录 owner、设备会话代次、开始/结束时间、当前大小、帧数和错误。停止与取消操作应幂等，重复请求不产生重复素材。

默认同一设备同一时间只允许一个独占录制会话；其他 viewer 可以查看状态，但不能无授权接管或停止他人的会话。设备断开、重连、编码器重启时必须明确记录会话边界，不能把不同会话的时间戳直接拼接。

### 5.3 同步操作录制

第一版同步记录**已通过统一输入分发层接受的操作**，不只是前端鼠标事件。覆盖手动触控、键盘、按键映射以及通过 Gamer Input/Touch 能力发送的脚本操作。对于直接绕过 Gamer、由游戏内部或 adb 外部工具产生的操作，不承诺可以捕获。

操作观察点应位于语义操作进入设备发送路径时，并允许保留来源信息；原始 touch down/move/up 与上层 tap/swipe 不得双重生成同一个脚本动作。建议记录原始输入事件流作为审计/重建依据，同时在独立层生成可编辑的语义事件（tap、swipe、key、wait 等）。同一 `operation_id` 或关联 ID 用于去重及关联，来源可标记 `manual`、`keymap`、`runner`、`plugin`。

```json
{
  "schema_version": 1,
  "event_id": "evt-001",
  "operation_id": "op-001",
  "session_id": "session-001",
  "source": "manual",
  "kind": "tap",
  "timeline_us": 1532000,
  "time_domain": "recording",
  "coordinate_space": "device-display",
  "display_size": { "width": 1920, "height": 1080 },
  "payload": { "x": 820, "y": 460 },
  "status": "accepted"
}
```

此结构仅为建议，最终字段应与现有 Input/Touch 契约和运行事件保持一致。连续触控保留 pointer ID、down/move/up 时间、轨迹及压力等必要信息，可压缩为语义 swipe，但不能丢失多指手势所需信息。脚本运行中的 find/if/loop 等控制语义可以作为辅助运行日志引用，不属于通用输入事件格式。

**时间同步要求：** 输入事件在服务端统一单调时钟域记录，录像启动时建立媒体 PTS 与单调时钟的映射；不可直接将前端 `Date.now()` 与视频 PTS 相减。视频时间轴使用整数微秒或其他明确的整数时间单位，并保存时间基准。播放器事件定位允许预览偏差，但模板精确帧和事件关联应使用确定的媒体帧时间戳。

文本输入、剪贴板内容等可能含敏感信息。V1 默认只记录动作类型、长度或脱敏摘要，不保存明文输入；如后续允许保存明文，必须单独显式选择并给出风险提示。录制会话默认不收集浏览器全局键盘输入，只观察真正发送给 Gamer 设备控制通道的操作。

### 5.4 操作草稿不是自动回放

视频工作台允许选择、删除、重新排序、添加注释或标记操作事件，再交给 `gamer.yaml` 生成 YAML v3 草稿。等待时间可以由事件间隔推导，但必须明确为建议值。无法映射的多指、复杂键盘、文本或未知输入应产生待人工处理的注释/诊断，不得默默丢弃或猜测。

最终脚本需要用户补充模板判断、状态等待、分支和异常恢复。录制数据绝不自动创建定时任务、自动启动 Runner 或在切回实时设备时执行。涉及购买、领取、消耗资源等一次性行为，运行前应由现有任务/脚本机制执行明确的用户确认和验证策略；本插件不提供绕过游戏限制的能力。

## 6. 媒体读取、离线帧与坐标

### 6.1 媒体导入与读取

媒体导入流程：上传或选择文件 → Core 校验与探测 → 安全落盘 → 生成 metadata → 按需生成兼容工作副本 → 注册到媒体库。不要只依赖扩展名判断格式，也不要把任意用户文件路径直接传给 shell。

V1 以 H.264/MP4 为主要播放兼容目标；对 MKV、MOV、H.265、AV1 等源文件先探测，能够直接播放和解码则保留原格式，不能直接播放但可安全转换时生成工作副本，无法支持时明确报错。实际支持矩阵以打包 FFmpeg、浏览器和平台测试结果为准，不承诺所有容器/编码都支持。原文件保持不变，转换任务可取消且受资源限制。

使用服务端媒体解码作为精确帧来源。对可变帧率视频，不按固定帧率计算目标位置；建立真实展示帧 PTS/帧索引映射，保证逐帧前进/后退和指定帧提取可重复。浏览器 `currentTime` 仅用于预览定位，不能作为精确模板素材的唯一依据。需要时允许先 seek 至前一个关键帧，再解码到目标展示帧。

### 6.2 FrameHandle 扩展

现有 FrameHandle 是不透明句柄，VisionService 已接收帧句柄。应延续这一设计，把实时帧与离线帧通过统一 Frame Provider 提供给视觉引擎，避免复制 NCC 实现。

建议新增 `FrameDescriptor`，包含来源类型、source ID、原始尺寸、工作尺寸、PTS/帧索引、校准版本、像素格式等元信息。FrameHandle 不直接暴露内存指针或磁盘路径；媒体帧在句柄存活期内保持不可变，引用计数/租约管理由 Core 负责。释放、过期、文件删除或校准版本变化后使用旧句柄应有明确错误。

当前 `FrameService` 的实时 `latest` 语义不应改成“当前舞台帧”；建议增加明确的 `media.frame_at(mediaId, target)` 或通用 `frame.open(source, selector)` 入口。现有实时调用保持原语义，离线调用必须显式传入素材和时间。视觉匹配结果保留来源及坐标信息，离线测试不需要连接 Android 设备。

### 6.3 分辨率与坐标模型

**1920×1080 是推荐参考环境，不是导入门槛，也不是所有模板的自动兼容保证。** Gamer 自录视频默认保留虚拟屏原始分辨率；外部素材允许其他分辨率和比例。导入时保留原视频尺寸、旋转、像素宽高比、有效画面区域、工作参考尺寸和变换信息。

统一定义四个空间：`encoded`（文件原始像素）→ `oriented`（应用旋转/像素宽高比后的画面）→ `content`（去除黑边或录屏边框的有效内容）→ `reference`（制作模板与脚本采用的参考画面）。浏览器 CSS 舞台坐标另作展示空间。所有裁切、匹配区域和点位变换必须使用同一套可逆的仿射映射或明确的等效坐标映射。

```text
原始视频帧
   → 旋转 / 像素比例修正
   → 用户确认有效画面区域
   → 等比缩放到参考工作尺寸（必要时补边）
   → 模板裁切 / 搜索区域 / 草稿坐标
```

不允许静默非等比拉伸。1920×1080、2560×1440 等相同比例素材可采用等比工作副本；非 16:9、竖屏、黑边和录屏软件边框必须显式校准。校准变化后旧模板和操作事件不能暗中被赋予新的坐标含义；需要保存校准版本，必要时提示重建工作副本。

模板导出应明确图片来自原始帧还是工作帧。优先使用与目标参考分辨率一致的工作帧制作模板，并在同一坐标系保存搜索区域；不要只缩放图片而不变换搜索区域和点击位置。生成的 YAML 坐标必须与目标设备的参考显示尺寸一致。目标设备尺寸或 UI 布局不同，应提示用户验证或重新校准，不能仅凭分辨率判定兼容。

此外检查游戏语言、UI 缩放、版本差异、平台压缩、锐化、HDR/SDR 与色彩变化。必要时生成标准 SDR 工作副本，但不承诺转换可恢复原视频丢失的细节。离线匹配通过后仍应在实时设备上验证。

## 7. 媒体库与 Package 数据

### 7.1 存储原则

全局媒体库管理大文件、媒体元数据、哈希、状态、引用和生命周期。Package 的视频插件目录只保存项目/会话工作数据与媒体逻辑引用；不得把大视频默认复制到每个 Package，也不得让 Core 理解视频插件的业务 JSON 结构。

建议概念结构如下，最终以当前 `data_dir` 与 PackageStore 实现为准：

```text
data/
├── media/
│   └── <media-id>/
│       ├── original.mp4
│       ├── metadata.json
│       ├── work/...
│       └── recording/...
└── packages/
    └── <package-id>/
        ├── package.toml
        ├── shared/
        └── plugins/
            ├── gamer.video/
            │   └── projects/...
            └── gamer.yaml/
                ├── automations/
                ├── functions/
                └── templates/
```

`media/` 的目录名和具体内部格式属于本计划拟定的新机制；`projects/` 属于 `gamer.video`，Core 不解释其内容。媒体库元数据可使用现有 SQLite 迁移体系管理，二进制文件仍放文件系统。建议使用不可猜测的 media ID、SHA-256、大小、时长、容器/codec、尺寸、创建时间、状态、引用数量及来源类型。文件导入采用临时文件、校验后原子提交；更新元数据和文件时考虑崩溃恢复，防止半导入资源被正常使用。

### 7.2 录制会话与制作项目

区分三层概念：

- **Media Asset**：原始视频及其工作副本，可由多个项目复用。
- **Recording Session**：一次录制的时间轴、视频片段、输入事件和同步关系。外部素材可以没有 Recording Session。
- **Video Project**：某个 Package 下的制作工作，保存素材引用、校准、片段标记、注释、所选事件及制作进度。

会话时间轴应支持一段或多段视频，以处理断流和编码参数变化。项目引用使用逻辑 ID 与版本/校验信息，不使用绝对路径。删除项目不自动删除全局原视频；删除仍被引用的媒体需提示，并由 Core 拒绝或要求用户明确解除引用。垃圾回收仅处理没有引用、没有活动租约且满足保留策略的资源。

### 7.3 Package 导入与导出

默认 `.gamerpkg` 继续导出 `package.toml`、`shared/`、`plugins/` 等 Package 数据。视频原文件不默认包含；插件项目中的媒体引用可以标记为 `external / missing`，导入目标没有对应素材时仍允许保留项目，并明确提示需要重新关联素材。缺少视频插件时维持 dormant plugin data 语义，不删除、不解释、不修改。

增加用户显式选择的“包含视频素材”导出模式。可以采用扩展现有 `.gamerpkg` 的媒体附件清单，或者单独制作素材归档；为减少格式复杂度，优先使用现有归档机制增加可选媒体附件，具体清单由通用归档层承载，业务引用由视频插件负责。打包时列出文件大小、总量和隐私提示，避免误分享账号录像。导入必须验证路径、哈希、大小、引用映射及空间配额，发生冲突时按既有 Package 覆盖/复制语义处理，不引入复杂 Merge。

## 8. Host API、权限与跨插件调用

### 8.1 Media Host API（拟新增）

下列是能力级设计，最终名称、异步方式和 WIT/Rust 形态应适配现有 Host API 版本体系：

```text
media.import             导入并探测素材
media.get / media.list   获取已授权媒体元数据
media.open_frame         获取指定时间/帧的不可变 FrameHandle
media.create_work_copy   按校准生成工作副本
media.record.start       开始设备录制会话
media.record.stop        停止/完成录制
media.record.status      查询会话状态
media.record.events      读取已授权会话的操作事件
media.release            释放媒体/帧租约
```

Core HTTP API 可以提供媒体上传、Range 播放、元数据、精确帧、录制状态等受控入口；这些入口与 Host API 共用同一 service，不能分别实现两套媒体逻辑。播放文件必须使用资源 ID 解析，不接受任意服务端绝对路径。上传、探测和转换任务应限制文件大小、时长、分辨率、像素数、并发、CPU/内存与输出空间，并对超时和恶意文件安全失败。

新权限建议细分为 `media.read`、`media.import`、`media.record`、`media.write`、`media.events.read` 等，具体以现有闭集权限枚举和版本校验机制实现。读取输入事件与普通播放权限应分开；录制不自动授予任意设备输入能力。不要为插件开放 `filesystem`、`shell`、`process` 或无限制 network 权限来绕过 Host API。新增 domain 后同步更新 catalog、manifest 校验、WIT、native adapter 和相关边界测试。

### 8.2 跨插件能力

建议补充通用的类型化命令/贡献调用机制（已有等价机制则复用），而不是为视频插件写死 `gamer.yaml` 依赖。视频插件可查找 `template.create_from_frame`、`vision.test_template`、`automation.create_draft` 等由目标插件声明的能力，并通过通用 Bridge 发送帧句柄、Package Context、建议名称、坐标/时间元数据和选中事件。

调用方必须检查能力是否安装、可用、版本匹配及权限是否授予。返回结构化结果或诊断，不直接修改其他插件内部状态。`gamer.yaml` 负责实际模板校验、资源保存、名称冲突处理、YAML v3 生成与编辑器打开；视频插件只负责发起请求和展示结果。若 YAML 插件未安装，视频录制、导入、播放、标记仍可正常工作，相应制作按钮显示缺少能力的提示。

## 9. 分阶段实施计划

各阶段按依赖顺序执行。每个阶段应形成可运行的纵向闭环、测试和完成记录，再进入下一阶段；不要先完成所有后端再集中补前端，也不要在业务功能完成后才补安全和数据边界。

### Phase 0：基线核对与契约设计

**目标：** 锁定当前真实代码落点和最小公共接口，避免重复实现。

任务：

- [ ] 阅读当前 `AGENTS.md`、V3 ADR、插件 manifest、Host API/WIT、UI Bridge、PackageStore 和 YAML/Keymap 输入路径。
- [ ] 绘制现有 scrcpy 编码帧分发、FFmpeg 解码和浏览器输入的真实调用链，标出统一录制与输入观察点。
- [ ] 核对现有任务运行与设备会话生命周期，确认舞台来源切换不影响后台 Runner。
- [ ] 定义 Media Asset、Recording Session、Video Project、FrameDescriptor、FrameTransform、InputEvent 的版本化契约。
- [ ] 明确媒体存储目录、SQLite 迁移、上传与文件读取权限、插件贡献接口。
- [ ] 增加设计 ADR 和必要的架构边界测试基线。

**验收：** 能指出每个新能力的拥有者、调用入口和权限；没有“为了方便把业务放进 Core”的悬空设计；所有拟新增接口与当前 API 版本体系一致。

### Phase 1：Core 媒体库与离线帧

**目标：** 不连接设备也能导入视频、准确读取指定帧并调用视觉引擎。

任务：

- [ ] 实现 MediaStore 的 ID、元数据、状态、哈希、配额、引用和安全文件管理。
- [ ] 实现导入、探测、格式兼容判断与按需工作副本任务。
- [ ] 从现有帧缓存中复用/抽取解码组件，保留实时 GOP 缓存原有用途。
- [ ] 建立离线 Frame Provider、确定帧时间戳/索引和帧租约机制。
- [ ] 让 VisionService 在真实离线帧上完成 match、match_many 和 color sample。
- [ ] 提供受控媒体查询、播放、精确帧读取入口及对应 Host API 权限。
- [ ] 增加导入失败、损坏文件、非法路径、并发解码、资源上限与删除引用测试。

**验收：** 断开设备后可导入 H.264 MP4，指定同一帧重复读取结果一致；对该帧的模板匹配不调用设备截图；导入异常不会留下可被正常引用的半成品。

### Phase 2：Core 录制与操作事件

**目标：** 服务端录制真实设备视频及同步输入事件，浏览器关闭后仍能完成录制。

任务：

- [ ] 在原始 scrcpy 编码帧分发处添加低开销、按需启用的录制订阅。
- [ ] 实现关键帧起录、PTS 处理、封装、停止、异常收尾和分段边界。
- [ ] 实现录制状态机、设备独占策略、磁盘/队列限制和故障恢复。
- [ ] 在统一输入分发层增加观察事件，覆盖手动、Keymap、Runner 和插件输入。
- [ ] 建立原始输入与语义事件去重、时间同步、会话关联和敏感文本默认脱敏。
- [ ] 保存事件日志及录制片段时间轴，提供读取和状态 API。
- [ ] 测试浏览器关闭、设备断线、录制中切换应用、重复停止、磁盘不足与编码参数变化。

**验收：** 一次真实点击与滑动能在录像相应时间轴找到，不重复生成语义动作；录制不依赖浏览器窗口；录制异常不会卡住实时投屏；不完整素材可明确识别和恢复/查看已保存部分。

### Phase 3：统一舞台与视频工作台插件

**目标：** 用户可以在现有 Console 内完成素材导入、录制、播放、逐帧和标记。

任务：

- [ ] 抽离 `StageSource`、实时/媒体 adapter、坐标换算和通用叠加层。
- [ ] 增加来源切换、媒体基本控制和服务端输入安全门禁。
- [ ] 实现 `gamer.video` 插件 manifest、权限、生命周期与面板贡献。
- [ ] 实现素材库（导入、录制、打开、重命名、删除、元数据、状态）。
- [ ] 实现时间轴（播放、暂停、seek、逐帧、倍速、事件跳转、片段标记、注释）。
- [ ] 实现有效画面校准、参考分辨率选择和工作副本预览。
- [ ] 实现 Video Project 的 Package 数据保存、恢复、素材缺失提示及插件卸载/重装数据保留。
- [ ] 验证多个浏览器来源独立、录像模式不能误触真机、切回实时不恢复旧输入状态。

**验收：** 安装插件出现工作台，卸载后业务页签消失但数据保留；无设备可看外部视频；实时与视频切换不影响原有设备连接；视频模式的鼠标/键盘不会操作真机。

### Phase 4：模板制作与 YAML 草稿集成

**目标：** 从一次性录像中实际产出可编辑模板和脚本草稿。

任务：

- [ ] 将模板裁切改为基于确定帧的通用工作流，移除“保存时重新抓最新设备截图”的隐式依赖。
- [ ] 通过通用插件贡献接口调用 `gamer.yaml` 的模板创建与资源保存能力。
- [ ] 支持在视频中选择帧、框选区域、创建模板并写入当前 Package 的 YAML 插件资源。
- [ ] 支持同一离线帧上的模板匹配测试、阈值/搜索区域调整与命中叠加。
- [ ] 实现操作事件选择和 YAML v3 草稿生成，支持 tap、swipe、key、wait 等可映射动作。
- [ ] 对不支持的输入生成明确诊断；保留事件来源和时间信息供人工参考。
- [ ] 支持从视频跳转到对应 YAML 编辑器位置，以及从草稿备注回到视频时间点（至少实现正向链接，双向为可选增强）。
- [ ] 验证缺少 `gamer.yaml` 时视频插件仍可独立运行。

**验收：** 使用导入的视频成功创建模板并保存到当前 Package；离线匹配结果可重现；用自录会话生成合法 YAML v3 草稿；不会自动执行草稿或修改真实设备。

### Phase 5：Package 分发、可靠性与平台兼容

**目标：** 完成素材生命周期和发布所需的兼容、安全与性能收口。

任务：

- [ ] 实现 Package 默认不含媒体的导出，以及显式包含素材的可选打包方案。
- [ ] 完成媒体引用重映射、缺失素材提示、导入校验、引用删除保护及垃圾回收。
- [ ] 验证 dormant plugin data、Package 覆盖/复制与未安装视频插件场景。
- [ ] 测试 Windows 完整包、Docker/直跑环境的 FFmpeg 路径与依赖发现，不依赖开发机绝对路径。
- [ ] 建立 H.264 MP4 主路径和其他容器/编码的实际兼容矩阵；不支持时有清晰错误。
- [ ] 测试 720p、1080p、1440p、4K、非 16:9、竖屏、黑边、旋转和 VFR 样本。
- [ ] 检查内存、CPU、录制码率、磁盘占用、并发解码及长时间录制的资源上限。
- [ ] 更新用户文档、开发者 API/WIT、架构测试、错误提示和操作录制隐私说明。

**验收：** 不附带素材的 Package 可正常导入并提示缺失引用；含媒体导出能够校验并重建引用；长时间录制和大视频导入不会无上限占用资源；现有实时投屏、YAML 和 Keymap 回归通过。

### Phase 6：端到端验收与收尾

**目标：** 用真实的一次性操作制作流程验证整套功能，而不是只验证播放器。

任务：

- [ ] 准备一段可重复测试的模拟操作录制夹具和一段真实设备录制样本。
- [ ] 完成“录制 → 事件记录 → 播放 → 精确帧 → 模板 → YAML 草稿 → 实时验证”的完整 E2E。
- [ ] 完成外部视频导入、缺失媒体、无设备、插件卸载/重装、Package 导入导出 E2E。
- [ ] 对一次性操作采用模拟目标或测试账号验证，不要求反复消耗真实资源。
- [ ] 更新 Architecture Guard、前端边界测试、所有相关单元/集成测试并运行项目正式构建。
- [ ] 对照本计划逐项检查完成状态，输出剩余问题和实际测试证据；未验证的真实设备/平台结果不得写成已通过。

**验收：** 用户能够从一段已录制操作中完成模板和脚本草稿制作，并在明确选择真实设备后进行验证；不存在绕过媒体来源或权限边界的隐式操作路径。

## 10. 关键测试矩阵

| 场景 | 必须验证的结果 |
| --- | --- |
| 无设备导入/播放 | 正常使用媒体和离线视觉，不触发 ADB 或设备截图 |
| 视频模式点击/键盘 | 所有舞台输入均不会发送至真实设备 |
| 后台任务正在运行时看录像 | 任务按原有生命周期运行，录像不伪造或抢占设备状态 |
| 浏览器关闭/刷新 | 服务端录制保持或按明确策略结束，不产生无状态任务 |
| 两个 viewer | 各自媒体来源独立，录制所有权和权限正确 |
| 录制中断/磁盘不足 | 状态可诊断，实时推流不被阻塞，已保存部分可恢复或明确不可用 |
| 真实输入与语义事件 | 点击、滑动、按键覆盖完整，不重复记录，时间戳可关联 |
| 敏感文本 | 默认不记录明文，导出前有隐私提示 |
| VFR/旋转/黑边 | 精确帧定位与坐标映射正确，未校准不静默拉伸 |
| 模板裁切 | 必须来自用户选定帧，不会抓取另一个来源的最新帧 |
| 视频生成 YAML | 合法 v3 草稿，未知动作有诊断，不自动执行 |
| 插件缺失/卸载 | Core 正常运行，业务 UI 消失，Package 数据保留 |
| Package 导出 | 默认不包含大视频，可选附件完整性和引用映射正确 |
| 恶意/损坏文件 | 无任意路径读取、命令注入、越界资源使用或半成品污染 |

性能指标先建立真实基线，再根据设备和平台设定可重复的预算。不要凭空规定“4K 一定实时逐帧”或“所有编码必定零转码”。至少记录实时投屏增量 CPU/内存、录制队列与丢帧、媒体探测/精确帧延迟、并发解码峰值、长录像磁盘占用和错误率。录制功能关闭时，不应引入持续 FFmpeg 进程、额外解码或明显的实时路径开销。

## 11. 实施约束与最终交付

1. **先复用，再扩展。** 复用现有 scrcpy 帧、FFmpeg、Vision、PackageStore、Host API、扩展 UI Bridge；不再造第二套视觉引擎、YAML 编辑器或设备管理器。
2. **Core 只管理机制。** 视频项目、模板格式和脚本语义归插件所有，架构边界由自动化测试锁定。
3. **不伪造设备。** Media Source 是离线只读来源；FrameHandle 可以来自媒体，但不能因此获得 Input/Touch 权限。
4. **数据和权限显式。** 全局媒体与 Package 数据分离，引用可追踪，文件访问和媒体事件读取按最小权限授权。
5. **原始素材不可变。** 校准、转码和标记使用工作副本或项目元数据；不要覆盖用户导入的原视频。
6. **没有 AI 依赖。** V1 使用确定性事件记录和人工制作流程；AI 辅助识别可在后续作为独立扩展接入。
7. **开发阶段不做旧架构兼容。** 必要时允许破坏性调整，删除过时实现；不为旧 Workspace、旧 YAML 或旧资源布局保留双轨。
8. **每阶段留下证据。** 代码、测试、文档与验收结果同步更新；遇到与当前代码不符的设计，应调整具体实现，但不得改变已确认的职责边界。

建议最终交付物包括：Core 媒体服务与离线帧 API、`gamer.video` 可安装插件、`gamer.yaml` 集成、录制事件格式与坐标规范、媒体/Package 导入导出支持、架构和 E2E 测试、用户使用说明、实际兼容矩阵与阶段完成报告。
