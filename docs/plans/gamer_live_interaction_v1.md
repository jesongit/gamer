# 直播互动触发 V1：常用规则与串行队列

日期：2026-09-26；实施更新：2026-09-27。状态：用户授权 go 后已实现首版，已完成下述本地验证，实机与真实直播验证待补。

已确认：同一设备上的互动操作按触发顺序排队，前一个函数或自动化结束后才能执行下一个，不插入或打断当前自动化。

本文保留讨论时的方案与验收目标。当前交付范围及与早期建议的差异以第 10 节和插件 README 为准，未完成的实机验证不计为通过。

## 1. 常用规则示例

以下函数名、自动化名均为玩法示例，并不代表配置包中已有这些资源。添加示例后默认停用；用户选择真实入口、补齐必填参数后才能启用。不预设游戏坐标，不自动向现有配置包写入游戏操作。

| 示例名称 | 收到什么 | 匹配条件 | 执行什么 | 参数示例 |
| --- | --- | --- | --- | --- |
| 弹幕跳跃 | 弹幕 | 去掉首尾空格后等于「跳」 | 配置包函数「跳跃」 | 次数 = 固定值 1 |
| 弹幕放技能 | 弹幕 | 等于「放技能」 | 配置包函数「释放技能」 | 技能 = 固定值「技能一」 |
| 弹幕切换角色 | 弹幕 | 等于「换人」 | 配置包函数「切换角色」 | 位置 = 固定值 2 |
| 弹幕开始挑战 | 弹幕 | 等于「开始挑战」 | 自动化「挑战一局.yaml」 | 难度 = 固定值「普通」 |
| 指定礼物放技能 | 礼物 | 礼物 ID 等于用户选定的礼物 | 配置包函数「释放技能」 | 次数 = 礼物数量 |
| 指定礼物触发挑战 | 礼物 | 礼物 ID 等于用户选定的礼物 | 自动化「挑战一局.yaml」 | 发起人 = 观众名字 |

V1 先支持弹幕和礼物，后续再按实际玩法增加点赞累计、关注或入场等条件。礼物 ID 从已收到的礼物消息选取，显示名称辅助识别，不猜测平台的礼物 ID。

每条礼物消息触发一次，礼物数量可传给函数参数，不直接把数量展开成同样数量的队列项。例如单条消息包含 5 个礼物，生成一项「释放技能，次数=5」。是否接受、限制或循环这个次数由函数定义决定。

同一条事件按规则列表从上到下匹配，仅首个条件命中的已启用规则获得处理资格，避免重叠规则重复执行。若该规则处于冷却或参数无效，则记录未入队原因，不继续匹配后续规则以绕过限制。规则顺序可调整；模拟预览展示匹配到的规则及未入队原因。

## 2. 一条规则的配置

规则包含：名称、启用状态、事件类型、匹配条件、动作类型、执行入口、参数绑定、可选冷却时间。

- 弹幕条件支持「等于」和「包含」，默认等于；不解析弹幕中的代码或任意表达式。
- 礼物条件按 ID 匹配，可选要求单条消息数量至少为某个值。
- 动作类型为配置包函数或自动化，入口列表与参数表单复用 gamer-yaml 的资源与参数描述接口。
- 每个参数可选「固定值」或「事件字段」；事件字段先开放弹幕内容、礼物 ID、礼物名称、礼物数量、观众名字、观众 ID。
- 可缺失字段不伪造默认值：绑定必填参数但事件缺字段时，显示「参数缺失，未入队」。
- 参数按入口声明的类型校验，不把任意文本自动转换成数字或代码。
- 未指定绑定的可选参数使用入口声明的默认值，并在入队时保存解析后的值；执行时仍做类型和必填校验，不重新套用已被修改的默认值。
- 冷却默认关闭；启用时按规则全局计时，从成功入队开始计算。冷却期间的命中显示「冷却中，未入队」。

规则保存在所属配置包的 gamer-live 插件数据中，可随配置包导入导出。设备绑定和直播凭据不写入可分发的规则。

## 3. 串行队列

一个互动会话明确选择一个目标设备和一个配置包。点击「启用触发」时固定本次目标；切换工作台正在查看的设备或配置包不会改写已有会话和队列。

执行过程：接收事件 → 去重 → 匹配规则 → 绑定并校验参数 → 入队 → 等待设备空闲 → 提交运行 → 等待终态 → 下一项。

- 设备已有手动运行、定时任务或互动运行时，队首保持等待。
- 队首遇到设备忙的提交冲突时留在原位置等待，不移到队尾、不标记失败、不越过它启动后面的项。
- 每项只有完成、失败或取消后才推进。单项参数/入口问题或操作失败不自动重试，保留原因并继续下一项；设备、权限或 Runner 等公共前提不可用时按第 6.1 节阻塞队列，不能逐项失败耗尽队列。
- 同一队列中严格 FIFO；本方案不改变手动运行和定时任务自身的调度规则，它们暂不自动加入互动队列。若需要所有来源一起排队，应另行明确统一调度范围。
- 入队时保存规则 ID/修订、规则名称、事件摘要、直播间/账号所属会话、设备、Android 目标、配置包、入口和解析后的参数。规则修改只影响以后收到的事件。
- 入队固定的是入口和参数，不是函数源码快照；执行时读取当前保存的函数/自动化，并重新校验。入口删除或参数不再兼容时该项明确失败；整个配置包丢失、被覆盖导入或设备 Android 目标变更时阻塞队列并等待用户处理，不猜测替代目标。
- 不因等待时间自动丢弃已入队项。建议首版最多 100 个等待项；满时新触发显示「队列已满，未入队」，不挤掉旧项。
- 无限循环或卡住的自动化会一直占用设备，后续项一直等待。界面显示正在等待的运行，并提供进入运行详情的入口。

例如设备正在运行「日常任务」，期间依次收到「跳」「放技能」「开始挑战」：

```text
执行中：日常任务
等待 1：跳跃（次数 1）
等待 2：释放技能（技能一）
等待 3：挑战一局（普通）
```

日常任务结束后依次执行 1、2、3；等待期间继续收到的有效互动排到末尾。

## 4. 页面与控制

保留「音视频输出 / 直播互动」两个子页签。直播互动页内为连接设置、互动规则、执行队列、最近互动；不重复显示与子页签相同的大标题。

互动规则提供「新增规则」「从常用示例添加」「编辑」「启用/停用」「调整顺序」「删除」。从示例添加只建立待完善的规则，不替用户启动执行。

### 4.1 运行队列管理区

直播互动页内提供常驻的「运行队列」管理区，规则编辑和连接设置可收起，让运行期间能直接查看和处理积压。沿用现有两个子页签，不新增顶层页面。

管理区按目标设备显示队列，顶部明确显示绑定设备、配置包、是否接收新触发、队列运行/暂停状态、等待数量与容量。首版管理直播触发的队列；已有手动运行或定时任务占用设备时，在当前运行位置展示其来源和等待原因，不把它伪装成互动队列项。

| 区域 | 展示内容 | 可用操作 |
| --- | --- | --- |
| 当前运行 | 名称、来源、开始时间/已运行时长；互动运行额外显示触发观众与规则 | 查看参数、日志；本队列发起的运行可取消 |
| 等待列表 | 顺序号、入口名称、观众、规则、入队时间/已等待时长、状态 | 展开参数、移除单项、勾选后批量移除 |
| 最近结果 | 成功/失败/取消/已移除、完成时间、简短原因 | 查看详情与日志；失败或取消项可手动重新入队 |

未启动项使用独立的队列项 ID；真正提交成功后才关联 run_id，不能把「已入队」显示为「已运行」。等待原因区分「队列已暂停」「等待前项完成」「设备正在执行其他运行」。不根据队列长度虚构预计完成时间。

首版保持严格先入先出，不提供拖动排序、插队或优先级。移除等待项后剩余项保持相对顺序；手动重新入队创建新项并排到末尾，保留原记录及关联关系，不覆盖原失败结果，也不自动连续重试。重新入队使用原入口与绑定参数并重新校验，可能再次产生已经部分执行过的动作，操作文字需明确为「重新执行并排到队尾」。

### 4.2 控制语义

| 控制 | 行为 |
| --- | --- |
| 启用/停用触发 | 控制新事件是否入队；停用不取消已入队内容 |
| 暂停/继续队列 | 控制下一项是否启动；暂停时当前项继续完成，新命中仍可排队 |
| 移除等待项 | 移除指定或勾选的尚未启动项，保留「已移除」结果 |
| 清空等待项 | 清空服务端处理此操作时尚未启动的项；当前运行继续完成，新触发仍可能入队 |
| 取消当前运行 | 向本队列发起的活动运行发送取消请求，显示「正在取消」，确认其终态后才能推进下一项；队列未暂停时会继续下一项 |
| 停止互动执行 | 停止接收新触发、暂停队列、清空等待项，并请求取消本队列发起的当前运行；不关闭音视频和直播消息连接 |
| 运行详情 | 打开对应 run_id 的现有日志；设备被外部手动/定时运行占用时，在其详情使用已有运行控制，不由「停止互动执行」代为取消 |

「停止互动执行」用于直播期间快速停止自动操作，须与只暂停下一项的「暂停队列」明确区分。取消是请求，不保证设备动作瞬间停止或撤销已经发生的动作；取消失败时保留当前运行和错误提示，不能显示为已停止。之后重新开始需要明确开启触发并继续队列。

队列操作以服务端状态为准：移除等待项时若它已开始运行，应返回「已开始运行，无法移除」并刷新状态，不暗中转成取消；批量移除逐项报告结果。暂停与启动下一项必须在同一调度控制下串行处理，暂停成功后不能再启动新的等待项；已进入启动/运行阶段的项属于当前运行，仍按取消流程管理。清空/暂停的结果提示包含处理数量与剩余状态，多页面刷新后应看到一致结果。

### 4.3 互动结果与测试

最近互动用平铺行显示：时间、观众、内容、命中规则、处理结果。处理结果包含未匹配、触发已停用、冷却中、参数错误、队列已满、等待中、执行中、成功、失败、取消；已启动项关联实际 run_id。

「模拟事件」默认只预览匹配结果和参数，不入队。用户明确点击「加入队列测试」才进入真实执行流程，测试事件要有明显标识。

## 5. 生命周期与实现边界

- 匹配和队列由服务端运行，关闭或刷新浏览器不影响执行，不使用 events.read 的前端轮询触发操作。
- 手动断开互动停止接收新消息，已入队项继续执行；页面明确提示，用户可另行暂停或清空队列。
- 临时网络重连期间保留队列，不从页面观察缓存重放历史消息来补触发。
- 停用插件停止接收和启动后续项，清空等待项；已经提交的运行继续由现有运行系统管理，可单独取消。
- 审阅后的建议：规则与队列记录持久保存，服务端重启后恢复为暂停状态，触发开关保持关闭；凭据不保存。重启不自动重放动作，恢复细则见第 6.2 节。此项取代初稿「重启丢弃队列」的建议，尚待用户确认。
- 复用现有事件归一化、去重和统一 Runner 提交入口；直播业务规则归 gamer-live，Core 不增加直播条件或 YAML 关键字。
- gamer-yaml 不可用时音视频和消息查看仍可用，触发功能明确显示依赖不可用；启动前重新检查权限、入口和参数。
- 涉及 host 实现与运行提交权限，需随 Gamer 本体发布，不能只部署前端 UI。

## 6. 审阅补充：需提前明确的边界

以下记录审阅时新增的设计建议；当前实施状态见第 9 节。优先补齐失败处理、恢复和事件判重；不为首版增加通用规则语言或多平台调度系统。

### 6.1 公共故障不能耗尽队列

队列区分「运行中」「手动暂停」「条件不可用」「恢复待确认」；与直播连接状态、是否接收新触发分别显示。

| 情况 | 建议处理 |
| --- | --- |
| 设备正在运行其他任务 | 队首等待，设备空闲后按原顺序尝试 |
| 设备暂时离线 | 保留队首和等待项，显示设备状态；允许既有连接机制正常重连，不因暂时离线把后续项逐个失败 |
| Runner/插件不可用、执行权限被撤销 | 阻塞整个队列；修复后由用户继续；新事件命中显示未入队原因 |
| 配置包丢失/覆盖导入、目标设备被删除、Android 应用目标改变 | 阻塞并停用新触发；用户处理旧队列或重新建立目标，不把旧队列改派给其他设备或配置包 |
| 某一项入口被删除、参数失效或游戏操作失败 | 该项失败并保留原因；公共执行前提仍正常时继续下一项 |
| 启动请求是否成功不确定、运行终态无法确认 | 保留该项并暂停后续提交，先按关联 run_id 核对；不能当作失败直接重复启动 |

设备掉线若导致当前运行失败，该项仍记录失败，同时阻塞后续项等待设备恢复。用户主动暂停期间设备恢复不能撤销手动暂停。暂时断网或离线可继续收取事件到有界队列；任何无法接受的触发都必须有未入队记录。

### 6.2 重启保留队列，但不自动继续游戏动作

建议把队列项与状态保存在本机运行数据中，不随配置包导出；保存成功后才向界面报告已入队或已移除。规则、队列记录和平台凭据各有独立生命周期，队列存储不包含连接密钥。

- 重启后尚未启动的项恢复为等待项，队列整体暂停，触发关闭；提示恢复了多少项，由用户选择继续或清空。
- 原先已执行完成的项只恢复为历史结果，不重新执行。
- 原先正在启动/运行的项先查询其 run_id 的持久运行记录；只有明确终态才更新结果。没有可靠记录的标记为「结果待核对」，阻止后续自动执行，不声称它失败或尚未执行。
- 对结果待核对项，允许用户选择「结束此项并继续后续」或明确「重新执行并排到队尾」；保留核对操作记录，不篡改为执行成功。
- 入队请求、手动重新入队等写操作应有请求 ID，网络重试返回原结果，不创建第二项。去重接受记录与队列入队在同一个持久提交中完成；执行提交与队列存储之间的不确定窗口必须能够识别并进入待核对状态。
- 存储失败时阻止新增和启动，显示错误，不能在未保存队列身份/状态时继续发起动作。
- 存储失败不能阻止「暂停队列」「停止接收新触发」或向已知 run_id 发送取消请求。这些停止动作先在当前进程生效，持久化失败单独报告；不能报告等待项已持久清空。重启后仍以暂停/待核对状态呈现旧记录，不自动重放。

这提供可检查的恢复流程，不宣称平台消息可靠补发或设备操作恰好执行一次。

### 6.3 事件身份、重连与连送礼物

现有观察缓存只按连接等信息做有界判重，不能直接充当触发队列。触发消费从服务端收到的规范化事件进入，不通过读取最近 500 条观察缓存补建队列；正常突发也不能因界面缓存淘汰而静默漏触发。

- 有稳定事件 ID 时，按平台、账号/直播间范围、事件类别和 ID 判重，普通网络重连不重置同一业务会话的判重记录。
- 缺失事件 ID 时只保证同一个本地已接受事件不会被内部重复消费；不按「相同观众+相同内容」去重，否则观众连续发两次「跳」会被错误合并。界面和文档不得承诺此类平台重投递也能完全去重。
- 首版弹幕规则只消费标准弹幕事件；镜像弹幕只展示，避免同一句话通过两个事件通道执行两次。
- 礼物数量究竟是每条消息增量还是连送累计量，实施前需核对适配器契约并用真实脱敏样本验证。规则使用已确认语义的单次数量；语义未确认的消息只展示并说明暂不能触发，不猜测增量。
- 开启触发以服务端生效点后的新事件为准，关闭期间收到的事件不在重新开启时补排。事件处理使用当时完整的一版规则，保存和重排规则不会让同一个事件跑两遍或混用不同版本字段。

### 6.4 修改规则与切换会话

停用/删除规则只影响后续触发。界面显示该规则还有多少等待项，提供独立的「移除此规则等待项」操作；不因编辑规则悄悄清空队列。

一个互动会话绑定设备、Android 目标、配置包和直播间/账号。普通重连属于同一会话；手动换账号或直播间、换目标设备/配置包前，应先停止新触发并处理旧队列（完成或清空等待项、结束当前运行）。不能把上一直播间的等待项自动带进下一直播间。

函数源码在执行时读取当前保存版本这一点需要在队列参数详情中说明。首版不做函数依赖图快照；编辑游戏操作前可暂停队列，清理不再适用的等待项。配置包覆盖导入属于整体内容更换，应阻塞并提示核对旧队列。

### 6.5 查询、日志与长队列

- 队列快照带递增修订号，前端丢弃过期响应；规则保存走现有资源乐观并发机制，多个页面编辑冲突应显示冲突而不是静默覆盖。
- 等待项和历史结果支持按状态/规则筛选及分页，列表保持平铺；可搜索观众名字，观众身份判定仍只使用平台身份字段。
- 未启动就被拒绝的触发也保留简短记录，不能只依赖 run_id 日志。执行中的详情仍复用现有运行日志。
- 等待项直到被执行或明确移除才消失；最近结果/未入队记录建议本地保留最近 7 天且最多 10000 条，先到限制先清理。待核对项不按历史清理，保留策略不影响现有运行日志自身规则；此数值为首版建议。
- 队列满、离线、暂停、存储失败在管理区持续显示，不能只弹一次消息后消失。等待列表过长仍能看到暂停和停止入口。

### 6.6 收尾检查：运行交接和长时间执行

- 队列推进不以浏览器显示「完成」、日志最后一行或前端计时为依据。服务端确认前项终态后仍须通过 Core 的设备互斥提交下一项；当前实现的终态通知与释放设备槽是不同阶段，遇到释放尚未完成或外部任务竞争时仍等待，不绕过运行守卫。
- 单项可选最长执行时间，默认不设限以免误杀正常长任务；从真正开始执行计时，等待和暂停期间不计入。达到上限后发出取消请求并显示「超时，正在取消」，确认终态和设备释放后再执行下一项；取消迟迟未完成时保留阻塞原因，不强行并发执行后项。
- 未设超时也要显示实际运行时长；在运行详情中保留取消入口。首版不自动判断游戏是否卡死，不因视频静止就终止自动化。
- 正常退出服务端、停用插件、点击「停止互动执行」三种动作分别沿用第 5 节及队列控制定义，不能混用恢复策略。停用时被清空的等待项应持久标为已移除，重新启用不能从磁盘把它们复活；处理未完成就崩溃时，恢复记录进入暂停/待核对流程。

### 6.7 首版范围与仍需决定的项

优先范围：弹幕/礼物条件、函数/自动化入口与参数、单设备串行队列、管理操作、模拟预览、可解释的失败处理、恢复待确认。暂不加入观众积分、礼物优先级、拖动插队、多设备分发、表达式脚本或点赞累计等玩法。

待确认的主要产品选择：

1. 是否采纳本次建议的「重启保留队列，恢复后暂停」；初稿为重启丢弃队列。
2. 是否只管理互动来源。当前方案对手动/定时运行沿用现有设备互斥，不能保证互动队首一定抢在新定时任务之前启动；所有来源一起公平排队需要扩大为通用运行队列。
3. 队列容量 100、历史 7 天/10000 条、冷却默认关闭、首个条件命中、断开连接后已有队列继续执行等默认行为是否适合实际使用。

第 8 节给出上述选择的推荐组合，供整体评审；推荐值不等于用户已经确认，不能据此宣称已授权实现或修改现有运行行为。

## 7. 验收重点

1. 弹幕精确/包含匹配、礼物 ID 和数量条件、规则首个命中及冷却符合配置。
2. 已有自动化占用设备时，新事件只入队；前项进入终态后才能启动后项。
3. 设备忙的竞争提交保留队首；失败项不堵死其后的正常项。
4. 参数缺失、资源删除、依赖不可用和队列满有明确结果，不能显示为已执行。
5. 暂停、继续、删除和清空只作用于各自约定的范围，切换页面不重置运行。
6. 同一个已接受事件不因 UI 刷新或内部重复消费被重复排队；有稳定平台事件 ID 的重复投递按定义的范围判重，缺失 ID 时不承诺识别平台重投递；礼物数量不自动展开成多个运行。
7. 模拟预览不触达设备；实际测试只有显式入队后才执行。
8. 单项/批量移除与启动竞争时反馈真实结果；清空不取消当前运行，暂停成功后不再启动新项。
9. 取消未确认完成时不得启动下一项；停止互动执行不影响音视频或外部手动/定时运行。
10. 手动重新入队生成新项并排到末尾，保留原结果、原始参数与关联关系；多个页面显示一致的服务端队列状态。
11. 公共依赖或设备故障阻塞队列，不逐项耗尽；手动暂停不会因设备恢复被自动解除。
12. 若采纳持久队列，重启恢复等待项为暂停状态，已完成项不重跑，结果不确定的运行进入待核对；保存失败不能报告入队成功。
13. 标准弹幕与镜像弹幕不双触发；重复事件 ID 不重排，没有事件 ID 的相同正文不能误合并；礼物连送数量有契约测试。
14. 停用/启用触发不补排停用期间消息；规则保存与消息处理交错仍使用一致版本；换直播间或执行目标不继承未处理的旧会话队列。
15. 过期页面响应不回退状态，存储与网络重试不重复入队；未入队原因可查，历史清理不删除等待或待核对项。
16. 终态通知早于设备槽释放时，下一项不能绕过互斥启动；单项超时只请求取消，取消尚未完成时仍不启动后项。
17. 存储故障仍允许暂停接收、暂停启动及取消已知活动运行，但不能谎报持久清空；停用后重新启用不恢复已明确移除的等待项。

## 8. 首版推荐组合与实施顺序

### 8.1 推荐默认值

| 项目 | 首版推荐 | 理由 |
| --- | --- | --- |
| 排队来源 | 仅直播互动，函数和自动化共用一条串行队列 | 实现已确认的互动玩法，避免同步改变现有手动/定时任务的产品行为 |
| 执行目标 | 一个明确绑定的设备、应用和配置包 | 排队内容不跟随当前浏览页面漂移 |
| 排队顺序 | 严格按服务端接受事件的顺序；同一批消息沿用接收顺序 | 平台时间戳可能相同或乱序，不能靠观众端时间重新排序 |
| 重启恢复 | 保存等待项和结果，重启后暂停、触发关闭 | 保留积压供核对，不自动恢复游戏操作 |
| 队列容量 | 最多 100 个等待项；当前运行另计 | 有界接收，不覆盖旧项；恢复后也适用同一容量定义 |
| 队列已满 | 新触发不入队，记录原因 | 不挤掉先到的项，不制造隐含的第二条等待队列 |
| 规则匹配 | 首个条件命中；默认弹幕精确匹配 | 防止一条消息执行多套动作 |
| 冷却 | 默认关闭，可按规则设置 | 先保证每次有效互动可解释，再按实际直播频率调整 |
| 等待过期 | 不自动过期 | 已接受的互动保留到执行或显式移除 |
| 单项失败 | 记录后继续；公共故障阻塞 | 单个玩法错误不堵住其他项，共同故障不耗尽整队 |
| 单项超时 | 默认不设限，可单独设置 | 不猜测不同游戏操作的正常耗时 |
| 手动断开直播 | 停收消息，已有队列继续 | 断开消息来源与停止已接受操作职责明确，界面同步提示 |
| 最近结果 | 最近 7 天、最多 10000 条，等待/待核对项除外 | 控制本机数据增长，同时保留近期排查依据 |

如果后续要求手动、定时与互动全部严格先来后到，应先调整统一运行提交与调度方案；不能只在直播插件里承诺全局公平顺序。

### 8.2 第一次使用的完整流程

1. 在配置包中准备实际函数或自动化；从直播页明确选择目标设备、配置包，展示设备的 Android 应用目标。
2. 连接直播消息，保持触发关闭。选择「从常用示例添加」，绑定真实入口，填写固定参数或事件字段，保存规则。
3. 使用「模拟事件」检查命中规则、参数、目标及未入队原因；这一步不操作设备。
4. 需要验证真实游戏动作时，显式选择「加入队列测试」。该操作可在直播触发关闭时使用，但仍要求有效目标、可用执行依赖和队列容量，并遵守暂停及先进先出规则，不绕过运行守卫。
5. 查看测试项的执行结果与日志；确认规则适用后开启直播触发。此后新消息在服务端匹配、入队，浏览器可关闭。
6. 直播过程中在队列管理区暂停、移除或查看结果；要停止后续及当前互动操作，使用「停止互动执行」。

### 8.3 实施分四步

| 顺序 | 工作内容 | 完成依据 |
| --- | --- | --- |
| 1. 规则与模拟 | gamer-live 内定义规则、条件匹配、参数绑定和 6 个示例；复用现有资源保存与入口参数接口 | 同一个模拟事件稳定得到相同命中与参数；规则编辑不触达设备 |
| 2. 队列与恢复 | 服务器维护单消费者 FIFO、持久项状态、操作幂等、暂停/清空/移除及恢复待核对 | 使用可控的假 Runner 验证顺序、故障和崩溃恢复，不需要真实设备 |
| 3. 接入现有执行 | 在组合根注入通用 Runner 提交/运行查询/取消能力；在事件归一化后接入触发处理 | 提交返回真实 run_id，日志可查询；设备冲突保留队首；取消确认前不启动后项 |
| 4. 页面与本机联调 | 规则表单、示例、模拟预览、队列列表与结果，更新宿主和本地安装插件 | 实际浏览器验证功能、滚动与刷新恢复，再用明确选定的测试函数验证设备执行顺序 |

运行权限需在插件 manifest、动作清单及服务端执行边界同步补齐：提交使用 run.submit，取消使用 run.control，并声明对应 host_api 契约；这是实现范围，不表示当前直播插件已有这些权限。gamer-yaml 缺失时仅禁用依赖它的互动执行，音视频与消息查看继续可用。

直播规则和队列归 gamer-live；通用运行接口只接收 Runner、执行入口、上下文及参数，不加入弹幕、礼物或 YAML 语义。需要补充的运行关联信息使用通用来源/请求身份，不让 Core 认识具体直播规则。

### 8.4 交付边界

- 交付时标明宿主版本与插件版本，插件源码先提交分仓，再更新主仓 gitlink；本次方案阶段不改版本或提交功能源码。
- 验证记录分清规则模拟、假 Runner、实际浏览器、真实设备和真实直播消息；未执行的项目明确标注，不把模拟测试当成平台实测。
- 真实礼物连送数量等平台适配仍需实际样本验证；普通设备测试使用已明确配置的入口，不借示例名称猜测点击位置。
- 当前评审阶段到此收敛，不继续增加玩法；后续实现以本文确认后的默认组合和第 7 节验收项为准。


## 9. 2026-09-27 实施结果与边界

宿主 0.2.2、gamer-live 0.2.1。规则、6 个停用示例、参数表单、预览、实际测试入队、FIFO、暂停/继续/停止、取消、批量移除、清空、重试、历史及完整 run_id 日志分页均已实现。规则归配置包，队列归本机运行数据。宿主只补通用入口参数绑定和 builtin 的退出生命周期，不引入直播业务或 YAML 新语法。

- 首版一个明确绑定目标、一条队列。100 个等待项一次完整返回；历史按状态筛选、每页 30 项，最近触发展示 100 条。观众搜索、历史按规则筛选暂未实现，不影响 FIFO 或管理操作。
- 重启后触发关闭、队列暂停；所有遗留活动项保守标为待核对，通过日志和现有运行状态核对后结束。不自动恢复或重新提交这些项。
- 停用插件清空等待项并请求取消当前互动运行；正常退出保留等待项。「停止互动执行」不取消手动或定时运行，不关闭音视频与消息连接。
- 设备已明确离线报错、Runner 不可用等公共前提阻止新入队并保留处理原因，已有队列暂停保留。空闲设备没有连接错误时允许既有 Runner 正常按需连接。
- 规则版本、入口、解析参数、目标与会话身份随队列项保存；函数源码不是快照。参数按 gamer-yaml 权威绑定器验证；gift_id 参数统一字符串，count 为整数。
- 礼物按官方 SEND_GIFT 的 gift_num 一条消息一项传参，不猜测连送累计差值。已覆盖官方格式契约测试；真实账号连送样本尚未验证。
- 历史/触发记录各最多 7 天和 10000 条，文件 16 MiB 预算允许提前清理旧历史；等待/待核对项不参与清理。稳定事件身份最多 7 天/20000 个；请求幂等有效期受对应记录保留限制。
- 队列满、存储失败、未知结果都有可见原因。文件损坏保留原文件，仅禁用互动队列，不阻止宿主启动或音视频功能。
- 内置动作权限测试、可控 Runner 状态测试、UI 测试、真实浏览器布局与本地 API 联调分别记录。当前无在线测试设备、无真实直播凭据，不能声称已完成实机游戏动作和直播平台端到端验收。

具体命令和验证结果见 `docs/evidence/LIVE_INTERACTION_2026_09_27.md`。后续实际玩法仍由用户选择已有配置包函数，不通过示例猜测坐标或创建游戏操作。


## 10. 2026-09-27 用户反馈后的简化（覆盖旧开关设计）

用户实际发送「日常」后，规则已开启但总触发关闭、队列暂停，导致未入队。用户要求每条规则只需自己的开关，取消多层启动设计。

- 页签统一为「直播设置 / 互动规则 / 触发日志」。设置包含输出、直播账号连接、互动执行设备与配置包；规则页只负责自定义规则与测试；消息、匹配结果、队列管理和运行历史归日志页。
- 删除触发总开关和常规暂停/继续操作，服务端不再保存 enabled 总闸状态。规则开关点击后立即按资源版本保存，不需再点保存或启动队列。
- 正常状态默认自动执行；开关开启后，仅新事件匹配入队，仍严格 FIFO，前项终态后才提交下一项。不补排旧弹幕，关闭规则不取消已经入队的动作。
- 规则内容编辑仍显式保存；新规则默认关闭，保存有效配置后可开启。开关提交失败保留原状态并显示原因，跨页面版本冲突拒绝覆盖。
- 重启无遗留任务时连接直播即可继续使用现有规则。只有遗留任务、未知运行或设备/存储故障才在日志页显示核对或恢复入口；这些异常处理不作为正常启用步骤。
- 保留取消当前运行、移除/清空等待项、失败重试、日志完整分页。插件停止仍拒绝接收后续消息并停止派发。

版本：宿主 0.2.3，gamer-live 0.2.2。旧第 3—9 节关于触发总开关与常规暂停启动的描述不再适用。
