# Gamer 插件分仓与图形启动器发行计划

> 日期：2026-09-24；状态：方案已确认，实施前先提交现有工作区；本计划对应程序尚未修改。
> 用户确认：允许手动启动健康旧版；可选插件更新不阻断启动；先完成启动器和发行流程，再迁移插件仓库。
> 适用首版：Windows x64。其他平台待有构建与测试条件后单独增加。
> 本文以当前代码为依据，补充并修订 AUTO_UPDATE_DEVELOPMENT_PLAN.md 的发行形态；旧文中的 Docker/GHCR、旧数据目录与旧 schema 基线不作为本次实施要求。

## 1. 目标与用户确认的行为（2026-09-24 修订）

采用“一个启动器 + 一个软件本体”的产品模式。后续要求覆盖前稿“GUI 退出、独立 manager 常驻”的设计。

- 直接以启动器 exe 所在目录作为安装根；不是快捷方式的“起始位置”或 shell 工作目录，不再要求选择安装目录。
- 首次未安装：显示图形安装界面，在当前目录安装本体、ADB、FFmpeg/FFprobe、scrcpy-server 和选中的官方插件。
- 已安装、文件状态正常、未发现可用更新：启动软件本体并自动收进系统托盘；启动器进程继续运行。
- 发现可用更新：显示图形更新界面，不自动启动本体。由用户选择更新；推荐允许明确点击“暂不更新，启动现有版本”，但不自动替用户跳过更新。
- 已安装文件缺失或变化：显示检查/修复进度，修复前不启动损坏版本。
- 支持暂停、续传、中断恢复；已完整校验且未变化的文件不重复做全量哈希。
- 图形启动器与现有 Gamer 工作台统一视觉设计；安装、更新、修复、启动在同一界面完成。
- 完整离线包携带经过验证的官方插件，首次由用户选择安装，不携带个人脚本、配置包、账号或设备数据。
- 首版 Windows x64，不默认开机自启、不注册 Windows 服务、不要求管理员权限。

插件仓库策略已确认：启动器和发行流程完成后迁移到独立 gamer-plugins 仓库，不使用长期插件专属分支；尚未执行远端迁移。

## 3. 插件仓库策略与推荐职责

### 独立仓库与新分支的选择

| 方案 | 特点 | 结论 |
|---|---|---|
| 独立 gamer-plugins 仓库 | 独立版本、Release、CI 和协作者；需要管理 SDK 与宿主固定依赖 | 符合长期独立维护/发布目标，推荐 |
| 同仓库 plugins 专属长期分支 | 分支是同一个项目的另一条历史，Release/tag 仍在同仓；联合修改需要跨分支同步 | 不用于模块拆分 |
| 同仓库、同分支保留 plugins 目录，独立工作流与插件 tag | 原子修改和本地联调最省事，也能独立发布插件 | 若暂时只需调整发布形式，可先采用，再择机分仓 |

分仓的收益是维护与发布边界，不会自动消除编译耦合。以下按已确认的独立仓库方案描述；迁移安排在启动器和发行流程验收后执行。

### 主仓库 gamer

- 稳定 Core、浏览器壳、图形启动器与后台管理引擎。
- SDK/WIT 契约、宿主兼容规则、依赖锁文件、发行脚本与本体 Release。
- 以 `plugins/` Git submodule 引入 `git@github.com:jesongit/gamer-plugins.git`，固定提交，不在构建时跟随分支最新提交。
- 发布记录保存主仓库提交、插件仓库提交、SDK 契约版本及实际安装包哈希。

### 插件仓库 gamer-plugins

- 三个官方插件的 manifest、host、guest/interpreter、UI、插件测试与构建入口。
- 插件按自己的版本发布 `.gplugin`，例如 tag `gamer-yaml-vX.Y.Z`，不要求三插件同步涨版本。
- 发布版本化的市场索引及 `.gplugin` 下载地址、哈希、权限、依赖、兼容要求。
- 普通用户从 HTTPS 下载产物，不需要 Git、SSH 密钥、Rust、Node 或 GitHub 账号。

### 分仓边界

1. 第一阶段是源码分仓和产物分发，不把现有 host 代码强行改成可动态加载库。
2. host 变更、builtin 执行体变更仍需要新版宿主；UI/WASM 更新在声明的宿主能力范围内可独立发布。
3. 插件独立构建必须使用固定版本的 SDK/WIT 发行材料，解除对兄弟仓库路径的隐式依赖。若测试需要主仓库，CI 显式 checkout 固定提交，不跟随 main。
4. 主仓库更新 submodule 前跑跨仓集成测试；插件的独立发布同样跑声明支持的宿主基线测试。
5. SDK 的依赖方向是插件依赖 SDK；SDK 构建不得反过来要求构建全部插件，避免循环流水线。
6. 迁移前清点当前未提交及未跟踪文件，保存可恢复副本；仅迁移源码与必要历史，不把 server/data、缓存、二进制、私钥或个人资源推到新仓库。先在隔离目录验证，再替换工作区的 plugins 目录。

## 4. 单启动器与托盘生命周期

```text
gamer-launcher.exe（唯一常驻启动器）
    ├─ 安装 / 更新 / 修复窗口
    ├─ 托盘菜单
    ├─ 下载续传、增量校验、状态与恢复
    └─ 服务监管、单实例锁、已有升级 IPC
             │
             ▼
       gamer-server.exe → 浏览器工作台
```

不再单独交付 gamer-manager.exe。之前拆分是为了界面进程完全退出；常驻托盘后这些职责都能复用在同一个启动器中。内部 GUI、下载和监管分模块/线程，耗时 I/O 不阻塞界面。

### 启动判断

1. 解析 exe 所在目录，确认属于本安装实例，取得单实例锁；已有实例则唤起它，不启动重复后端。
2. 恢复中断 journal，并行执行本地快速检查与有界更新检查（网络等待上限默认 3 秒，不含必要本地检查时间）。
3. 未安装：打开安装窗口；有离线 seeds 时默认安装包内版本，不强制联网追最新。
4. 有已确认可用更新：打开更新窗口，不先启动本体再停掉。目标必须经可信渠道确认且匹配平台、升级范围与插件兼容要求。
   此门禁覆盖本体、启动器及必需依赖；可选插件的独立更新只提示。必须配合本体更新的插件纳入同一更新计划。
5. 有待恢复安装或文件异常：打开恢复/校验/修复窗口，不隐藏错误或启动半成品。
6. 已安装且健康、未发现可用更新：窗口无需展开，托盘显示“正在启动”；就绪后打开浏览器工作台，保留托盘图标。
7. 网络超时/不可达且没有此前已确认可用更新：允许健康旧版本正常启动，状态写“更新检查未完成”，不谎报“已是最新”。若已有已确认更新记录，仍显示更新窗口及离线启动按钮。
8. 后续才查到更新且本体已经运行：托盘通知并标记更新入口，不自动停程序或强行抢焦点。运行期间手动打开启动器可下载更新，安装仍受工作负载守卫约束。

是否启动本体以明确状态驱动，不能由多个异步请求各自触发，防止“先启动后发现更新”的竞态。首次安装/更新成功后默认自动启动；所选插件失败须用户处理或明确跳过后再收起。

### 托盘与窗口行为

- 左键/双击托盘恢复启动器窗口；菜单提供打开工作台、检查更新、暂停/继续当前下载、修复、停止本体、退出 Gamer。
- 窗口关闭按钮 X = 收到托盘；不等于退出或取消下载，首次收起提示一次。最小化也进入托盘。
- 暂停按钮立即保存下载状态；再次打开窗口继续同一任务。托盘“退出 Gamer”在下载阶段可保存进度后退出，原子提交阶段安全收尾后退出。
- 本体运行时“退出 Gamer”通过现有停机接口处理任务/录制守卫，再等待本安装实例 server 退出；不留下失去管理的孤立 server，不误杀其他安装实例。
- 关闭浏览器不停止后台任务；停止本体后启动器可留在托盘等待再次启动。
- 托盘注册失败或系统托盘重建时，重新注册；无法恢复就显示窗口，不能把唯一控制入口隐藏掉。
- 不依赖 Android 设备在线才能启动工作台；启动失败、端口占用或浏览器打开失败时恢复界面并提供可读错误/地址。
- 所有后台子进程不弹控制台，监管使用准确进程句柄和安装实例身份。

## 5. 界面与统一视觉设计

视觉基准是 `web/src/styles/theme.css` 和当前工作台组件：深灰背景、暖黄色主按钮、相同字体与图标风格、3/4px 圆角、紧凑但清晰的间距。不能另做一套游戏海报风、不同强调色或不一致按钮语义。

主界面布局：顶部产品与当前版本；中部显示安装/更新说明；下部为组件清单、进度与主操作按钮。日志默认折叠，普通用户无需理解 manifest、SHA 或内部路径。安装位置显示为当前目录，只读；目录不可写时提示将整个目录移动到可写位置。

- **安装页**：本体/依赖大小、官方插件选择及权限、当前目录、所需空间、“安装并启动”。
- **更新页**：当前版本 → 目标版本、更新说明、本次需下载大小、兼容提示、“更新并启动”；健康旧版提供显式“暂不更新，启动现有版本”。
- **进度页**：下载/校验/安装/启动阶段、速度、已完成大小、组件状态、暂停/继续。不同阶段不显示虚假百分比。
- **异常页**：失败文件或阶段、原因、重试/修复/日志入口，不自动消失。
- **已安装页**：启动/打开工作台、检查更新、完整校验、停止本体。

实现路线优先验证 Rust 原生 GUI + 托盘，复用现有 Rust 引擎；设计 token 从现有主题提取为共用规格，原生控件映射同一颜色/字体/尺寸，不能长期维护两套分叉主题。技术验证包括中文、DPI、键盘操作、虚拟机/远程桌面、无独显、系统托盘与无控制台启动。

若原生方案达不到统一视觉要求，再选 Tauri + Vue 直接共享主题/组件；必须先解决缺少 WebView2 时连安装界面也打不开的问题，并明确在线原生引导与完整离线运行时。尚未锁定 GUI 库版本，正式实现前完成一页界面与托盘验证；不为选型重写当前工作台。

## 7. 版本清单、更新源与兼容

- 每个版本的清单固定本体、启动器、ADB、FFmpeg/FFprobe、scrcpy-server 的版本、URL、大小、SHA-256 和逐文件校验。
- 推荐插件集合固定插件 ID、版本、归档哈希及宿主要求。插件自身依赖继续使用现有插件依赖模型。
- 渠道入口只发现目标版本；后续只消费该目标的不可变清单，不对每个组件分别请求 latest。用户普通启动不静默换安装版本。
- 相同依赖可引用旧 Release 的固定资产，并按哈希复用缓存；不为每次本体发布伪造一个新的 ADB/FFmpeg 版本。
- scrcpy 改独立组件后，原有 app 内相对路径、repair、环境注入、doctor、manifest schema 和测试必须一起调整；消除 app/seed 各一份的隐式双来源。
- 现有 manifest v1 使用严格未知字段拒绝，不能直接塞入 启动器/插件/文件清单新字段后假定旧启动器能读。先确定 schema 新版与最低启动器版本；旧版本至少给出明确更新启动器路径，不实现无价值的多代兼容层。
- 实际已分发版本在实施前盘点；若必须跨一次旧版入口，设计单次显式桥接发行，不允许直接覆盖不可读清单导致旧安装无法恢复。
- 插件安装和市场都要执行宿主版本/API 能力检查；兼容性权威在服务端，不能只在启动器 UI 过滤。builtin 能力与原生函数新增需要相应宿主能力门禁。
- 本体启动不失败于插件市场不可达。已安装插件不被推荐集合悄悄覆盖或降级；升级前检查现有插件对目标宿主的兼容性，并展示必要处理。
- 官方稳定索引和试验索引分开；市场展示可以变化，已选下载目标的版本与哈希不能在重试中漂移。
- Release 继续使用已有清单签名链；插件沿用现有 `.gplugin` 校验与权限流程，不顺带另造插件签名体系。离线官方插件哈希由已签名的本体发行清单固定。

## 8. 安装目录与离线一致性

复用现有 config/data/logs/state/versions/runtime/cache/staging/backups 布局；增加持久校验记录、下载恢复状态和插件 seeds。启动器直接位于安装根。

- 本体版本目录只放可替换程序，用户数据和已安装插件状态保持在稳定数据域。
- 安装根恒为启动器 exe 所在目录，完整包恒为解压根。快捷方式工作目录不改变安装根；无目录选择页、不自动改到 AppData/Program Files。当前目录不可写或文件冲突时提示移动目录，不默认提权，不覆盖无关文件。
- 在线/离线走同一安装引擎，来源次序为：已验证安装 → 匹配的离线 seed/缓存 → 明确的远端地址。
- 完整包首次默认安装自身发行版本；若在即将启动前已确认有可用更新，切到更新页，不自动启动本体。断网可安装并启动包内版本。
- 离线包缺少所选组件时明确指出缺项，不能无限等待网络；取消插件选择可继续安装本体。
- 首次安装同时检查磁盘可用空间（压缩包 + 解压 + staging；升级还需备份），中文、空格、长路径和目标卷原子切换能力。
- 不依赖机器预装 ADB/FFmpeg、开发工具或 PATH。现有外部 ADB server 冲突提示具体原因，不随意 kill 其他工具的 ADB。
- 首版不增加注册表安装器、驱动安装、复杂卸载器或多平台产品矩阵。

## 9. 安装官方插件

1. 用户选择插件，展示功能、必要依赖、权限和已验证版本。
2. 下载或读取相同版本的离线 `.gplugin`，核对清单哈希。
3. 本体就绪后，经现有本机管理认证和插件安装接口安装；不由启动器直接写入插件目录。
4. 服务端执行版本/能力/权限/依赖验证，再 enable/start。
5. 插件失败显示单独结果，支持重试或明确选择“先使用工作台”；本体已安装成功不需要整体删除或重装。
6. 用户选中插件的结果未处理前，窗口不自动收进托盘。运行后仍可在工作台插件中心管理。

离线包内 `.gplugin` 只是安装资源；不复制开发环境的已安装目录、运行状态、token 或配置包。空环境沿用现有默认配置包播种机制。

## 10. 更新、修复与恢复

- 每次启动先执行第 4 节状态判断：有更新显示启动器、不自动开本体；未发现更新才自动启动并托盘化。旧版本的手动启动不代表忽略已有更新记录。
- 下载可在运行时进行；安装前由服务端统一判定运行、录制、写事务与调度状态，符合条件再进入维护阶段。
- 复用 journal、离线一致性快照、候选 activation gate、健康检查与提交/回滚。插件安装状态、配置和数据库需纳入对应版本恢复边界。
- 预提交失败恢复旧程序与升级前数据；新版本已正常使用后的降级不承诺无损，明确展示备份恢复范围。
- 修复只替换清单声明的受管程序/组件，不扫描覆盖用户脚本、配置包或媒体。
- 稳定清单指定组件版本，不按目录名取最高版本作为运行依赖；升级前后都用同一配方。
- 启动器自更新复用短生命周期 trampoline/替换助手，运行中的 exe 不覆盖自身；安装锁和 server 监管必须完成可验证交接，不能启动两个服务实例。新入口确认可用后删除临时助手，失败恢复旧入口。该助手不是常驻 manager，也不是额外产品。
- 安装中断电、进程被结束、下载中断后，重启从 journal 恢复或给出明确恢复入口；不只靠目录存在判断“安装成功”。
- 错误日志落在固定目录；界面显示阶段和可读原因，敏感令牌不进日志或命令行。默认不自动反复重启失败程序。

### 10.1 暂停、断点续传与安装恢复

当前 fetch.rs 在失败时删除 .part，不满足续传要求，必须实改；不能把已有 .part 临时文件视为已支持断点续传。

- 每项下载保存目标版本/哈希/大小、已落盘偏移、来源与强 ETag 等信息，临时文件按目标哈希寻址。暂停/断网/正常退出保留 .part 与状态。
- 恢复时使用 Range，存在有效强验证器时使用 If-Range；检查 206 与 Content-Range 起点/总长。若返回 200、验证器改变、区间不合法等，不能直接追加，重新获取该未完成产物。
- 已下载完成且仍与校验缓存一致的其他产物不重下、不重算哈希。目标版本改变时，只有哈希相同的文件可复用。
- 未完成的大文件不是“已完整校验文件”；恢复后可以重新读取已有前缀建立哈希状态，避免依赖不稳定的哈希内部状态序列化。下载完成的整体摘要必须匹配清单，才进入安装。
- 校验以文件为最小可持久化完成单元：中断后保留已通过文件的结果，仅继续未完成/变化的文件；单个文件校验中断允许从该文件开头重新开始。
- 安装过程有 journal；解压在 staging 中，每文件写临时路径后替换。恢复只复用有记录且仍匹配的已完成文件；不把半解压文件当完成。
- 原子切换、数据库迁移和快照恢复不是任意字节可暂停的任务；用户请求中断后在安全边界停下，明确显示“正在安全结束”。强制断电则下次按 journal 恢复。
- 下载成功、文件校验通过、安装完成、健康激活是不同状态，只有最后一项满足才标记该版本可启动。

### 10.2 增量校验与缓存失效

1. 初次下载/安装，对归档和落地的受管文件完成清单要求的 SHA-256 校验，成功后原子写入记录。
2. 记录绑定安装实例、清单摘要、相对路径、目标文件哈希、文件大小、最后写入时间及可用的文件身份；记录不是孤立的“已校验”布尔值。
3. 下次启动只对比文件存在性和轻量元数据；记录仍有效的文件直接复用结果，不全量读取文件内容。
4. 文件新增、身份/大小/时间变化、缺失、目标哈希变化或记录损坏时，只对相应文件重新校验/修复。新版清单可复用内容哈希相同且未变化的文件，不能因本体版本号变动把所有依赖缓存清空。
5. 清单要覆盖本体 exe、前端资产、运行依赖；已安装插件需使用其实际安装版本对应的清单，不把用户独立升级的插件按旧推荐版本回退。用户配置、数据库、脚本和媒体不属于静态文件校验对象。
6. 提供“完整校验/修复”主动重算全部受管文件。元数据缓存是启动性能优化，无法证明内容在保持所有元数据不变时绝对未变；不把它宣称为逐次完整内容验证。
7. 同一轮安装产生的有效校验结果传递给后续阶段，消除 cache 命中、解压后、启动前对同一不变文件的重复全量计算。健康检查仍要执行，不能用哈希缓存代替程序是否可运行的检查。
8. 校验记录更新需有一致性检查，失败/部分写入记录不可被当成通过；安装目录移动/文件系统身份变化时重新建立必要记录。

## 11. 发行流程

1. 锁定主仓库提交、插件仓库提交、SDK/WIT 与第三方依赖。
2. 构建并测试本体、单启动器和官方插件，核对实际版本与声明。
3. 插件仓库发布不可变插件资产；候选联合验收可先消费 CI 工件，主仓库不得因等待同一轮发布形成循环依赖。
4. 主仓库生成候选清单，组装 full，在线与离线采用完全相同的组件字节。
5. 从实际发布暂存资产重新下载校验，不仅验证构建目录。
6. 在干净 Windows 环境验收，再发布正式版本，最后更新稳定渠道入口。
7. 保留前一稳定版本及其组件资产。固定 tag 下不覆盖同名不同内容文件；更换字节必须产生新版本或构建标识。

## 13. 必须通过的验收矩阵

- 无 Rust/Node/Git/ADB/FFmpeg/预置配置：单独 GUI 下载并安装成功。
- 断网机器：完整包安装到打开工作台、安装选定官方插件均无需网络。
- 带中文/空格/长路径目录；无写权限、磁盘不足、端口占用均有可读提示。
- 双击两次、已有后台实例、已有另一个安装目录：不错误接管或启动重复 server。
- 下载超时、断网、HTTP 限流、哈希错误、清单签名错误：不启动半成品，可重试或恢复。
- 自动启动后只有一个启动器托盘进程；窗口隐藏后运行、定时任务、插件、设备连接正常；托盘和再次双击均能恢复原实例。
- 关闭浏览器不停止任务；明确停止操作遵循运行守卫，退出 Gamer 后不遗留本安装实例的 launcher/server。
- 无设备时正常进入工作台；连接设备后投屏、输入、模板截图通过；媒体导入/帧表验证 ffprobe 确实由受管目录提供。
- scrcpy jar 不匹配必须在连接前报告；不会自动更换到另一协议版本。
- 官方插件安装失败、依赖缺失、权限变更、旧宿主不兼容都有明确处理；未勾选插件不安装。
- 启动器/本体/插件更新后保留用户资源、设备、任务与配置；故障注入验证快照和预提交回滚。
- 暂停/退出/断网后重启可以续传；已完成且未变化的产物不重新下载/哈希。Range 不支持、ETag 改变、返回区间错误时不追加损坏文件。
- 增量校验可观察到哈希调用次数：第二次正常启动不重算已通过文件；只改一个文件只重验相应文件；记录损坏不会直接跳过；手动完整校验确实重算。
- 有可信可用更新时不自动启动本体；更新检查超时能启动健康旧版但正确标记未知；已有更新缓存时仍显示窗口。
- 关闭窗口只收进托盘；显式退出在安全边界保存进度；断电后的安装/迁移状态可恢复。
- 从不同 shell/快捷方式启动始终使用 exe 所在目录；不写入另一个安装目录。主题颜色/字体/按钮与工作台对照验收。
- 发布产物不含 server/data、开发密码、令牌、个人配置或私钥。
