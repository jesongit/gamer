# Gamer AI 自动化完整开发计划

本计划以“录制演示 → 导出素材包 → AI 生成新 YAML 与模板 → 全素材验证 → 正常执行 → 根据运行记录进行 AI 调试”为完整目标。视频、自动化和 AI 助手三个现有插件分别扩展，不新增独立的 AI 自动化插件。

采用重新设计的新 YAML，优先面向视觉状态驱动、AI 生成和人工阅读。允许破坏性升级，不为旧语法建立长期兼容层。复用现有目标能力、插件调用、自动化执行、模板匹配和运行记录；不增加独立 Agent 平台、大型测试平台或游戏模拟器。

当前实施安排：先完成云电脑内的环境准备、代码改动、构建和本地自动化测试；真实设备、实际游戏和真实模型调用验证按后续安排进行，不作为开始或完成不依赖它们的本地开发阶段的阻塞条件。下文验收标准保留完整目标，未执行的实测必须单独列出，不能用本地测试替代。本文是开发计划，不表示所列新功能已经实现。当前范围包括发布准备，不包含自动推送仓库、发布插件或创建 Release；实际发布另行确认。

## 一 范围与代码基线

核查基线为 Gamer 主仓库 `ad402a40f1883314d7f0ff7ed03502ec8cb0cbf9`，插件子模块 `913ccf8b6bd1f3029a57cbc6e8d4f16782e9671e`。以下“已有”指该基线的代码能力；未据此宣称已经完成新方案的运行验收。实施前应重新检查最新提交，避免覆盖后续开发。

### 当前可复用的能力

- 视频侧已有录制会话、操作事件、媒体索引、精确帧提取、项目标记、区域框选和模板制作入口。
- 自动化侧已有 YAML 解释执行、原生函数、模板匹配、条件与等待、运行管理、脚本编辑及步骤记录。当前录制转草稿位于自动化插件，主要把操作转成坐标动作与等待时间，并非语义化生成。
- 静态图片模板测试已经存在，不需要连接设备；解释器也有可替换宿主能力的边界，可以扩展为素材回放执行。
- AI 助手已有模型配置、真实图片能力探测、供应商协议、预算、对话、记忆及设备操作。无设备对话已支持，但没有完整的离线素材生成、脚本编辑和自动化 Trace 调试工具。
- 宿主已有插件依赖与受控跨插件调用、资源版本检查、目标能力和运行互斥。需要扩展现有机制，不重新实现一套。

### 当前不能直接当作成品复用的部分

- 录制事件与文件帧之间存在静态时间域契约不一致的疑点，需要先通过真实标记录制验证。手势结束坐标、持续时间、具名按键及 START／END 信息也需补齐。
- 现有视频项目和媒体导出不等于自包含素材包，操作记录及录制分段信息不能漏掉。
- 现有等待实现包含直接读取真实时钟的逻辑，离线快速回放不能只替换截图和 sleep。
- 现有运行日志与步骤 Trace 不包含完整的图片证据链；其中某些 `frame_id` 表示调用栈帧，不是图像帧。
- 脚本运行时已有部分程序快照，但模板会读取可变资源；AI 修改入口也缺少完整的脚本与模板联合回退机制。

## 二 最终职责与依赖

### 视频插件

负责录制、时间对齐、帧提取、素材预处理、质量提示和素材包导入导出。只记录“发生了什么”，不决定业务流程，不生成 YAML，不解释“领奖成功”等游戏语义。

用户可以为素材补充名称、目标说明和 START／END 标记。停止录制只代表录制结束，不能自动等同于任务成功。

### 自动化插件

负责新 YAML、模板与脚本资源、素材验证、AI 生成流程编排、候选版本、运行记录关联、正式保存及回退。决定生成结果是否满足验证门槛，不能让模型自行宣布通过。

AI 生成功能是自动化插件的可选功能。正常运行、编辑、模板测试、素材验证和历史回看均不依赖 AI。

### AI 助手插件

保留现有对话、游玩和记忆功能，增加两类能力：

1. 为自动化插件提供受控的多模态生成与修订能力，复用模型连接、探测、预算和请求诊断。
2. 在对话中读取用户选定的自动化、模板、素材验证结果和运行记录，给出建议，或按授权提出并应用修改。

生成和调试不要求连接设备，也不占用 AI 游玩的设备控制租约。模型凭据仍由 AI 助手私有保存，自动化插件只获取能力状态和调用结果。

### Core 与 Automation Engine

Core 继续负责目标 I/O、录制媒体基础能力、运行生命周期、资源与插件调用约束。引擎负责确定性执行、取消、时钟、步骤事件和错误定位；不加入模型调用逻辑。

视频不硬依赖自动化或 AI。自动化对 AI 使用可选依赖；AI 通过受控工具调用自动化能力，避免相互必需的插件依赖环。导出的自包含素材离开视频插件后仍可验证，视频插件不是运行脚本的前置条件。

## 三 关键设计约束

### 素材包保持简单且可携带

采用一个包目录或压缩包，包含以下概念，不先建设额外数据库：

- 包说明：格式版本、素材 ID、来源、创建信息、内容指纹、录制是否完整及质量警告。
- 目标信息：目标类别、原始宽高、方向、必要的显示区域和坐标转换信息，不保存设备凭据。
- 时间信息：统一的相对时间轴、分段关系、帧索引与媒体时间映射；相同时刻保留稳定顺序。
- 操作序列：稳定事件 ID、类型、时刻、起止坐标、持续时间、按键等；区分实际采集与人工补充。
- 画面证据：START、操作前、操作后及 END 的原尺寸帧，必要的过渡帧与等待窗口，注明每张图的真实来源时刻。
- 目标说明：用户希望完成什么，哪些画面能证明完成，哪些条件尚未定义。
- 可选原视频：便于追加取帧，不是包可用性的隐含前提；若包不含原视频，必须自带本次验证所需证据。

不只保存“每次点击时的一张图”。否则很难验证点击后的结果、等待条件、可选弹窗缺失和最后一次操作是否生效。避免一次性导出每帧；按动作与状态变化选取证据，并在不足时明确要求补充素材。

长期素材与临时 Trace 分开管理。模板仍归配置包的现有模板体系，生成记录只引用素材及其版本，不复制一份独立模板库。

### 新 YAML 与同一套执行语义

重新设计语法，但保留底层能力复用。明确视觉目标、等待、点击、可选步骤、分支、循环、函数、参数、失败与结束条件；只有实际需要的语义才进入首版。

- 等待只观察，不隐式点击。观察得到的目标与随后动作有明确关系，避免已有 wait_find 默认点击行为造成双击。
- 必需步骤超时明确失败；可选步骤缺失可以跳过，但不能吞掉语法错误、设备断开和模板资源缺失。
- 可选步骤是否等待、等待多久必须有一致定义，不能依赖模型自行解释。
- 所有等待和循环有可控终止边界。保留少量显式 sleep 处理确有需要的节奏，不鼓励拿录制间隔堆成脚本。
- 脚本应描述任务完成条件，不能仅因执行到最后一行就声称达成游戏目标。
- 新语法保留来源定位和稳定步骤身份，使报错、Trace、生成建议能回到 YAML 对应步骤。

先实现最小可执行的新语法，再用真实生成与验证反馈完善。新语法可转成引擎内部表示，或演进现有解释器；生产执行与素材验证必须共用解析、分支、等待和错误语义。不要先让 AI 自由输出一套“暂时不能真正执行”的 YAML，再单独开发一个验证解释器。

### 全素材验证的含义

验证应证明：在每份已选择素材所记录的画面和操作约束下，脚本存在一条符合证据、可走到已定义目标的路径。它不能证明游戏会对任意新操作产生相同结果，也不能证明未出现过的分支正确。

所有选中素材都通过，才允许保存为“已验证的最终生成结果”。失败可以保存为候选草稿，便于继续工作；不得改名为成功、悄悄删掉失败素材或让 AI 修改验证样本来过关。

## 四 分阶段开发

### 阶段 0 核对基线并确定最小契约

**目标**：把跨插件边界和现有缺口先确认，防止后续各写一套。

**主要改动**

- [ ] 重新检查最新主仓库及插件提交，列明实际修改范围与现成能力。
- [ ] 确定素材格式、新语法最小范围、验证结果分类、生成候选状态和 Trace 事件关系。
- [ ] 明确脚本、模板、素材、模型配置与验证报告的版本关联规则。
- [ ] 先用合成帧、录制单元测试和已有合法测试数据核查时间映射；另列带明显标记的 Android／CDP 真实录制实测，覆盖分段、暂停或重连，留待设备可用时执行。
- [ ] 核查 raw touch 到 tap／swipe 的归并、最终 UP 坐标、持续时间、按键类型和停止时未完成手势。
- [ ] 确定插件宿主版本要求及需要随主程序发布的能力。

**本地验收**：形成简短的架构与契约说明，时间域映射具备确定性测试，标明静态疑点与测试结论。

**后续实测**：用真实标记录制确认各后端对齐；在完成前保留“未做真实录制验证”，不声称已复现或排除实际设备上的错位，也不因此阻止后续本地开发。

### 阶段 1 完善视频录制与操作对齐

**责任**：视频插件与 Core。依赖阶段 0。

- [ ] 统一录制会话时间、操作事件与媒体文件时间的转换；帧选择使用真实索引和整数时间，不靠浏览器浮点秒反推。
- [ ] 补齐 START／END，区分正常完成、用户停止、录制失败和设备中断。
- [ ] 完整保存 tap、swipe、长按及 key 所需信息；不支持的多点触控或输入类型必须明确标记。
- [ ] 避免用固定 300ms 等猜测值冒充真实手势时长；事件记录时刻和动作完成时刻分别表达。
- [ ] 对画面尺寸、方向或显示区域变化建立清楚边界；首版无法支持时拒绝混为同一坐标空间。
- [ ] 录制开始无画面、输入先于首帧、事件落在分段空隙、重复帧及异常结束都有可解释结果。

**本地验收**：合成操作与帧序列中的动作能准确定位前后画面，关键动作信息不丢失、不静默伪造，现有录制与播放相关测试通过。

**后续实测**：实际手动操作的 Android／CDP 录制与回放，确认动作、画面和时长一致。

### 阶段 2 增加素材包生成与导入导出

**责任**：视频插件。依赖阶段 1。

- [ ] 在录制结果增加“生成素材包”，选择范围、填写目标、确认 START／END 和必要标记。
- [ ] 自动提取操作前后帧、关键等待窗口及完成画面，保留完整操作记录和来源映射。
- [ ] 预处理保持确定性和可重做；用户可以预览、补选帧，不能将抽帧失败当作素材完成。
- [ ] 输出自包含素材包；原视频不随包时，清楚显示后续不能从缺失视频补帧的限制。
- [ ] 导入检查格式、资源完整性、内容指纹、尺寸、事件顺序和时间映射；未知版本给出明确提示。
- [ ] 普通外部视频没有操作日志时，允许作为视觉参考，不能假装它具有完整操作演示和完整流程验证能力。
- [ ] 下线或替换视频侧“直接生成脚本”的主入口；无需维持旧录制草稿流程作为第二条长期主线。

**本地验收**：素材移到另一配置包或隔离测试目录、切断原录制目录引用后，仍可查看和验证。质量不合格的素材在进入 AI 之前就能看到原因；跨电脑导入留作后续补充实测。

### 阶段 3 升级新 YAML 与执行引擎

**责任**：自动化插件与 Automation Engine。阶段 0 后可与录制改造并行。

- [ ] 用最小实例确定新语法：稳定主流程、可选确认、两条分支、视觉等待、失败与成功条件、函数复用及 Trace 开关。
- [ ] 实现同一套解析、校验与执行语义，复用现有模板、输入、资源和任务机制。
- [ ] 抽出可替换的时间来源，保证等待与轮询也使用它；只替换 sleep 不足以支持虚拟时间。
- [ ] 明确匹配结果的新鲜度、坐标空间和目标代次；不能沿用过期观察直接操作其他设备或尺寸。
- [ ] 新语法中的函数调用、参数和错误位置使用现有注册信息，不为 AI 再建一份函数真相源。
- [ ] 运行开始冻结脚本、函数及模板的有效版本，或按明确规则拒绝执行期间被改动的资源；记录可还原快照。
- [ ] 新旧语法按版本明确区分，不静默误解析。开发期直接升级仓库内示例、函数库、测试与文档，不建设双引擎兼容层。

**本地验收**：人工编写的新 YAML 在实际引擎配合测试宿主下执行并准确定位错误；可选条件不误吞异常，等待不会隐式多点一次，取消和超时行为可靠。

**后续实测**：在真实目标运行相同语义的脚本，检查输入效果、观察新鲜度和设备生命周期。

### 阶段 4 建立离线素材验证

**责任**：自动化插件与引擎。依赖阶段 2、3。

- [ ] 为同一引擎提供素材回放宿主：画面来自素材，时间来自虚拟时钟，输入转为待核对动作。
- [ ] 复用正式模板匹配实现、参数与坐标规则，在实际素材图上测试命中、未命中及误命中。
- [ ] 按真实时间顺序推进等待和分支；不任意跳到未来一张“刚好匹配”的图，不先看 END 再倒推步骤成功。
- [ ] 核对操作目标、顺序及必要手势属性。允许合理坐标容差和录制中的冗余操作差异，但差异必须有规则和报告，不能任意跳过。
- [ ] 验证每份素材的入口、必要操作、可选路径及最终目标；最后一个点击之后仍要检查结果画面。
- [ ] 区分“通过”“逻辑或匹配失败”“证据不足”“不支持”，后三者都不能成为最终通过。
- [ ] 将模板缺失、误匹配、动作不对齐、等待超时、目标未达成和未覆盖分支输出为定位明确的诊断。
- [ ] 禁止回放宿主向真实设备注入输入，或执行启动应用、网络通知等外部副作用。

**验收**：同一候选在同一素材上重复运行结果一致；有确认与无确认的素材均按正确路径到达目标，故意损坏模板或结束条件能被发现。回放快于真实等待，且超时语义不因此改变。

### 阶段 5 扩展 AI 助手的自动化协作能力

**责任**：AI 助手、自动化插件和必要的插件调用适配。阶段 0 后可并行准备。

- [ ] 增加设备无关的多模态生成与修订调用，复用现有供应商、连接、取消、预算和诊断能力。
- [ ] AI 助手新增受控工具：读取脚本与模板、读取素材与验证结果、查询运行记录、提交候选改动及请求验证。
- [ ] 读取与修改分开；模型不能获得任意文件读写、任意命令执行或模板目录的无限权限。
- [ ] 自动化入口同时在 UI 和服务端检查 AI 插件安装、启用、模型配置、所需视觉能力及版本是否满足。
- [ ] 能力探测绑定模型配置版本；更换端点、模型或协议后不能沿用旧的通过结果。未知能力提示先测试，不按模型名称猜测。
- [ ] 图片、脚本和日志按本次任务需要发送给用户配置的模型；展示数据范围和费用来源，不自动上传全库。
- [ ] 切换配置包、停用插件、取消任务或更换配置后，晚到结果只能回到原候选上下文，不能写进当前新项目。

**本地验收**：以模型协议桩验证无设备的生成与分析调用、能力状态、取消和迟到结果处理；无 AI 时普通自动化照常工作。

**后续实测**：用户配置的真实模型图片理解、工具调用、预算和失败行为。协议桩通过不等于模型能力已实测。

### 阶段 6 完成多素材生成与修正闭环

**责任**：自动化插件主导，AI 助手提供模型能力。依赖阶段 4、5。

- [ ] 用户选择一个或多个素材、目标脚本位置与生成目标，开始一个独立候选版本。
- [ ] AI 分析共同主流程、可选步骤、分支、稳定目标及等待条件；不把一次演示中的全部点击和延时机械复制。
- [ ] 候选模板由实际素材区域提取，保留来源。所有试验脚本和模板进入暂存区，不能先污染正式模板库。
- [ ] 自动运行全部选中素材，向 AI 提供精简而完整的失败证据，再修改候选并重验全部素材。
- [ ] 为修正过程设置次数、耗时和模型预算边界，支持取消。达到边界或缺少证据时停止并说明，不承诺无限循环必然收敛。
- [ ] 原始素材、目标和通过标准保持不变；AI 不得删除失败样本、放宽目标或降低校验强度来换取成功。
- [ ] 用户可以修改候选，但任何脚本、模板、参数或素材版本变化都会使旧报告失效并触发重验。
- [ ] 全部通过后展示脚本、模板、分支说明、覆盖范围、未覆盖情况及报告，用户确认保存为正式版本。
- [ ] 脚本、模板及版本记录一起提交；冲突、取消或写入失败时不留下半套正式资源。保存前检查资源版本，避免覆盖用户同期修改。

**本地验收**：通过固定素材与模型返回桩，验证 A／C 有确认、B 无确认的候选路径、自动重验、失败不可排除及最终保存门槛。保存后的脚本不调用 AI 也可由引擎执行，失败候选只标为草稿。

**后续实测**：真实模型从未提供答案的多份演示自主生成、修正并通过验证；据实际效果评估分支理解，不能用预置响应宣称 AI 生成质量达标。

### 阶段 7 增加 Runtime Trace 图片证据

**责任**：自动化插件与 Core。依赖阶段 3，可与生成闭环并行。

- [ ] 复用现有运行 ID、日志和步骤事件，关联源步骤、脚本版本、模板版本、匹配区域、阈值、结果和异常。
- [ ] 图像使用独立身份，关联实际捕获时刻、被哪次识别使用及来源目标；不要混用现有调用栈 frame_id。
- [ ] 优先保存识别实际使用的画面，再补必要动作边界、明显变化及异常画面。事后补抓的当前图必须另标，不能冒充失败当时的图。
- [ ] 在可用帧源上做轻量变化检测、去重、最小间隔和数量控制；需要补充观察时使用受限频率，不承诺捕获任意两次观察之间的所有变化。
- [ ] 核查各后端真实成本。Android 与 CDP 分别复用可用来源；CDP 并不始终有现成的完整解码流，不能假设后台截图免费。
- [ ] trace 开关只控制自动图片采集，基本日志、步骤和异常继续记录。关闭和重新开启时各保存一张，异常时无论开关状态都尝试保存。
- [ ] 断连等情况下无法抓图时，保留最后一张图及其真实时间，并记录失败原因；不得伪造“当前画面”。
- [ ] 保存原始宽高与无损图像，优先评估 WebP Lossless；压缩异步且队列有界，必要时降频或停止自动采集并提示。
- [ ] 对已是有损的视频帧，只承诺导出后不再降质；无损编码不能恢复原始录像已经丢失的信息。

**保存策略**

- 完成运行的 Trace 图片及诊断载荷默认约保留 24 小时，成功与失败一致；容量超限优先清理最旧的已结束 Trace。
- 现有基本运行日志有自己的保留策略，不因新增 Trace 就全部改成 24 小时。清理后仍能看见运行摘要和“图片已过期”。
- 长运行采用单次运行和总量限制，不能为了“活动运行不清理”无限占盘；超限时停止或减少后续自动采集并记录缺口。
- 临时 Trace 清理不能删除素材包、正式模板和版本回退数据。用户显式保留或转为长期样本的内容走独立生命周期。

**本地验收**：用持续变化的合成帧验证开关、错误证据、队列和容量限制，完成压缩与磁盘基准测试，成功运行可事后回看。

**后续实测**：长时间真实战斗、Android／CDP 抓图成本及输入延迟；未实测前不承诺具体性能或所有动态变化均被捕获。

### 阶段 8 完成 AI 调试与安全修改回退

**责任**：AI 助手和自动化插件。依赖阶段 6、7。

- [ ] 对话可附加一个自动化或具体运行；“最近一次相关运行”按配置包、脚本、目标和时间筛选，不只取全局最新记录。
- [ ] 明确显示将分析的运行与脚本版本；存在多个候选时让用户选择，避免把另一设备的结果拿来解释。
- [ ] 先读取摘要、失败步骤和关键图片，需要时再加载更多记录，避免整段日志与全部图片一次塞给模型。
- [ ] 结合脚本、模板、命中记录和画面，区分模板失效、等待错误、新分支、逻辑错误、timeout 与环境异常；证据缺失时明确不确定。
- [ ] AI 先提出建议或候选修改。用户同意后，走与生成一致的验证、版本检查和整体提交过程，不直接覆盖正式文件。
- [ ] 保留上一版本的脚本及关联模板，支持查看差异和整套回退；回退后重新标记适用验证状态。
- [ ] 运行快照与当前编辑版本不同，必须基于差异处理，不能拿旧运行的脚本直接覆盖新版本。
- [ ] 如用户要求实际试跑，走现有运行管理与设备权限。AI 游玩正在运行或暂停但仍持有租约时，先明确处理控制权，不嵌套启动第二个设备运行。

**本地验收**：以固定运行记录和模型返回桩验证“刚才战斗结束没领奖”的记录选择、证据读取、授权边界、修改提交及回退；Trace 过期状态明确，重启不恢复设备操作。

**后续实测**：真实模型对实际故障的诊断与修改质量，以及用户批准后的设备试跑效果。

### 阶段 9 收敛前端与日常使用流程

**责任**：三个插件前端。与各功能同步建设，本阶段集中收尾。

- [ ] 视频：录制结果 → 生成素材 → 检查质量 → 导出或选择使用。
- [ ] 自动化：选择素材 → AI 生成 → 查看候选 → 全素材验证 → 保存 → 运行；每个失败状态显示具体原因。
- [ ] 脚本区以 AI 生成、AI 修改和 YAML 原文为主，保留模板选择、框选、参数说明、语法错误及步骤定位等真正有用的辅助工具。
- [ ] 不重做完整的新可视化编排器。旧编辑器无法表达新语法时切到只读或原文，不允许保存时丢失未知字段。
- [ ] 运行记录使用现有列表，详情增加统一时间线：步骤与日志按时间排列，图片以缩略图关联，点击展开原图、匹配框和模板。
- [ ] 提供“交给 AI 分析”“保留此记录”及“从此画面建立样本”的轻入口，不建设独立调试工作台。
- [ ] 区分“素材验证”“图片匹配测试”“真实设备运行”；设备相关操作明确提示目标，离线按钮不被设备连接状态误禁用。
- [ ] Trace 图片过期、采集关闭、超限和缺帧都可见；模型不可用不阻止查看已有结果。

**验收**：无需学习一套新工作台即可完成主流程；手机宽度或窄窗口下重要状态和按钮不被隐藏。新语法经过原文编辑后不会被旧表单破坏。

### 阶段 10 完整本地验收与发布准备

**责任**：主仓库与各插件共同完成。依赖前述功能。

- [ ] 建立固定样本集合，覆盖正常路径、可选弹窗、不同分支、误匹配、缺帧、超时和明确失败结局。
- [ ] 增加未参与生成的验证素材，识别对训练演示过拟合；与用户选中的必过素材分开展示覆盖结果。
- [ ] 对比 Android 与 CDP，覆盖不同分辨率、方向变化、断连、取消、并发编辑、插件停用和模型配置变化。
- [ ] 检查长运行性能、图片压缩、磁盘上限、24 小时清理、活跃记录保护及错误抓图失败。
- [ ] 验证导出导入后的素材、脚本和模板完整性，以及候选提交失败、历史回退、升级后的资源版本行为。
- [ ] 整理后续真实设备、游戏和模型验收清单；待具备条件并获准后做受控验收，区分“离线素材通过”和“此环境真实执行通过”，不将前者包装成后者。
- [ ] 更新 README、插件说明、语法文档、素材格式说明、示例和用户操作流程；删除误导性的旧入口文案。
- [ ] 准备主程序宿主能力、插件版本和插件子模块指针的协同发布变更。需要 Rust 宿主能力的修改必须随 Gamer 发布，不只更新 UI 归档；未经单独授权不执行远程推送或正式发布。

**本地验收**：使用合成数据、固定素材及协议桩，录制数据处理到生成编排、验证、运行、调试和回退链路可重复测试；无 AI 的基础自动化独立可用。发布说明写清破坏性语法升级及最低宿主要求。

**最终实测状态**：真实设备、游戏和模型验收仍是单列待办，不能因为本地实现完成而标记通过。发布材料准备完成也不等于已推送或已发布。

## 五 必须保留的边界

1. **输入覆盖**：有些游戏操作来自物理手柄、系统快捷键或其他程序，未经过 Gamer 的输入链路就可能没有记录。素材必须声明缺口，不能由 AI 猜造原始事件。
2. **视觉差异**：语言、主题、缩放、DPI、黑边、窗口尺寸和动态目标都可能影响模板。先明确每个脚本支持范围，不自动宣称跨环境通用。
3. **目标完整性**：END 只是时间边界。真正完成必须有画面或明确可验证条件；“已经点击领奖”不等于“奖励已领取”。
4. **回放边界**：录制只能证明已有证据上的路径，无法反事实模拟一次新点击。无依据的分支、无法核对的操作和证据不足应阻止最终通过。
5. **变更边界**：修改模板或阈值、切换素材及更新语法版本都会影响验证有效性；正式结果要绑定实际内容版本，不绑定一个可变文件名。
6. **数据边界**：截图、文本输入和日志可能包含聊天、账号或敏感信息。导出与发送模型前给出可审查范围，必要时排除内容；排除造成证据不足时如实提示。
7. **安全边界**：素材注释、截图文字和历史日志是待分析内容，不能授权模型操作设备、导出凭据或越权修改文件。导入包也要检查路径和资源上限。
8. **异步边界**：请求超时、模型重试、前端刷新和插件停用可能产生迟到结果。候选使用原始上下文和版本校验，不自动跳转到当前配置包。
9. **诊断边界**：自动图片记录有采样与容量限制，Trace 关闭期间只有边界和错误证据。界面与 AI 都必须知道这段信息缺口。

## 六 推荐实施顺序与完成标准

推荐顺序：阶段 0 → 阶段 1 与阶段 3、5 并行 → 阶段 2 → 阶段 4 → 阶段 6 → 阶段 8 → 阶段 10。阶段 7 在阶段 3 完成必要步骤事件后并行推进；阶段 9 随各功能落地，最后统一收尾。

先做视频素材与最小新语法，再做可重复的离线验证，之后才接多素材 AI 生成。这样 AI 生成第一天就有客观校验标准，而不是先积累大量“看起来合理”的脚本。Trace 和 AI 调试继续完成整个方案，不因为生成能用就视作全部结束。

### 每阶段完成后的汇报约定

每完成一个阶段，提供一次简短但完整的报告，固定包含：

1. 本阶段具体改了哪些功能和边界。
2. 从项目开始至今累计完成了什么，当前处于哪一阶段。
3. 实际执行了哪些构建或测试，以及通过、失败或未执行的准确结果。
4. 仍未验证的部分、已知问题和阻塞，尤其是设备、游戏和真实模型验证。
5. 下一阶段准备完成什么，以及是否需要用户提供条件或作出决定。

阶段报告区分“代码与本地验证完成”和“真实场景验收通过”。暂缓实测时可以继续不依赖它的开发，但相关风险保持开放，不将功能已实现写成全部场景已验证。若新代码发现原计划假设不成立，先报告影响与最小调整，再继续实施。

最终交付必须同时满足：

- [ ] 视频能导出可携带、时间对齐、包含操作与足够画面证据的素材包。
- [ ] 新 YAML 可读、可编辑、可真实执行；生产与离线验证没有两套冲突语义。
- [ ] 自动化插件具备多素材 AI 生成、全部验证、有限修正和正式版本保存。
- [ ] AI 助手未安装或不可用时，已有脚本仍可运行和维护。
- [ ] Runtime Trace 有可靠关联、开关、异常证据、24 小时及容量管理。
- [ ] 用户能从运行记录让 AI 分析问题，授权修改后可验证、提交和回退。
- [ ] 不引入独立 AI 自动化插件、通用 Agent 平台、双语法长期兼容层或大型游戏模拟测试系统。
