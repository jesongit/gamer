## Changes

Production authentication supports `GAMER_COOKIE_SECURE=false` for HTTP and true
for HTTPS independently of `GAMER_PROFILE=prod`. The environment overrides
`[auth].cookie_secure`; absent configuration retains prod=true/dev=false.
New Docker configuration explicitly selects HTTP. Existing volumes require an
explicit policy; changing the environment requires recreating the container.
Password verification, HttpOnly/SameSite, session expiry/revocation and Origin
checks remain enabled. No database migration or credential reset is included.

The Chromium seccomp profile now allows close_range/openat2 and returns ENOSYS for
clone3, retaining the existing sandbox. Restore recovery validates a previously
restored volume before reusing it, preserving the original key and stopped failed
container instead of extracting again. See the separate runtime recovery evidence.

## Resource and deployment boundary

BuildKit RUN processes used a temporary cgroup with 6 GiB hard / 4 GiB high memory
limits, no swap and one Cargo job. Recorded peak: 4295581696 bytes; memory max,
OOM and OOM-kill events were all zero. The empty temporary cgroup was removed.
Backup and test helpers were capped at 512 MiB without swap; fixture services at
2 GiB. Raw receipts/logs are under ignored `server/target/docker-release-v1.0.2/`.

Publication does not replace the destination container. Original local production
remains stopped; original data, migration archive and full rollback backups remain
preserved. Destination LAN browser/account and actual scheduled-run acceptance are
still performed after the operator's update. No ARM64, USB or real-account/game
success is claimed by these isolated tests.

Operator update instructions in `docs/guides/DOCKER.md` require a cold backup and
retain the old stopped container with restart disabled. Reuse
`gamer-production-data:/data`, set prod + explicit false, and do not run
init/restore/activate for an existing active installation.
